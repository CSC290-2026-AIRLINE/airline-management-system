# Database Structure

The database layer is centrally designed, modeled, and maintained exclusively by the Database Leads/Team. Feature teams do not directly write Prisma models or generate migrations. Feature teams specify domain requirements, while the DB team translates them into normalized tables, constraints, relations, and managed migrations.

## Folder skeleton

```
database/
├── prisma/
│   ├── schema.prisma     # single source of truth for every model, all teams edit this file
│   └── migrations/        # auto-generated by Prisma, timestamped folders — never hand-edit or rename
├── seeds/
│   └── <module>.seed.ts   # one seed file per module
├── schema-docs/
│   └── <module>.md        # one page per module: what tables it owns, what each field means
├── ERD.md                 # whole-system entity relationship diagram, updated at contract-freeze points
└── README.md
```

## Adding or changing a model

1. Add your model(s) to `schema.prisma`, inside a clearly commented block for your module:
   ```prisma
   // ─── booking-pnr (G03) ───────────────────────────
   model Reservation {
     id          String   @id @default(uuid())
     ...
     @@map("reservations")
   }
   ```
2. Run `pnpm prisma migrate dev --name g03_create_pnr_tables` — this generates a timestamped migration folder automatically. Include your team ID in the `--name` so the generated folder name shows ownership at a glance.
3. Commit both the `schema.prisma` change and the generated migration folder together, in the same PR.

## Table naming

**No module prefix on table/model names** — names should read like plain domain entities, not be namespaced by team or module:

```
Reservation
SeatHold
RefundLedger
CrewPairing
```

Prisma model names are PascalCase by convention; the underlying Postgres table name is set explicitly with `@@map(...)`, snake_case equivalent (`reservations`, `seat_holds`, `refund_ledger`, `crew_pairings`).

**Collision risk is real without a prefix.** Before adding a new model, search `schema.prisma` for a name that might already be taken or close to it (`Reservation` vs `Booking`, `Ticket` vs `Fare`, etc.) — DB leads are the backstop catching this in review, but check first rather than relying on them to catch it every time.

## Rules

1. **You only add/edit models inside your module's commented block in `schema.prisma`.** Because it's one shared file, keep your diff scoped to your block — don't reformat or touch other teams' sections in the same PR.

2. **Migrations are append-only and machine-generated.** Never hand-edit a migration file after it's merged, never rename or delete a migration folder — if something's wrong, write a new migration that fixes it.

3. **Cross-module relations (foreign keys) need DB lead approval before the PR is opened**, not during review. If `Reservation` needs a relation to `PassengerProfile`, talk to the DB lead and the owning team first.

4. **No shared "god models."** Each module owns its own data. If two modules seem to need the same table, that's a sign the boundary is wrong — raise it with DB leads rather than sharing a model across teams.

5. **`schema-docs/<module>.md` is required before your first migration merges.** One page: what tables you own, what each field means, what it's used for.

6. **`ERD.md` is not kept live day-to-day.** DB leads update it at the week 3–4 API/schema freeze point, and again before major demos.

## Migration review

Every PR touching `schema.prisma` or `prisma/migrations/` follows the same PR rules as everywhere else — 2 approvals + Code Owner review, currently `database-leads` for all of `/database/`:
- 2 approvals minimum
- DB lead approval (auto-requested via `CODEOWNERS`)
- If it adds a cross-module relation: that module's team lead approval too

## Status

Structure may still shift slightly once DB leads finalize the initial schema pass. `CODEOWNERS` currently owns all of `/database/` under `database-leads` as a whole — this is expected to stay broad rather than split per-module, since the shared-file nature of `schema.prisma` means DB leads review everything here regardless of module.
