# Database Structure

The database layer is centrally designed, modeled, and maintained exclusively by the Database Leads/Team. Feature teams do not directly write Prisma models or generate migrations. Feature teams specify domain requirements, while the DB team translates them into normalized tables, constraints, relations, and managed migrations.

## Folder skeleton

```
db/
├── prisma/
│   ├── schema.prisma     # single source of truth for every model, maintained exclusively by DB Leads
│   └── migrations/        # auto-generated by Prisma, timestamped folders — never hand-edit or rename
├── seeds/
│   └── <module>.seed.ts   # one seed file per module
├── schema-docs/
│   └── <module>.md        # one page per module: what tables it owns, what each field means
├── ERD.md                 # whole-system entity relationship diagram, updated at contract-freeze points
└── README.md
```

## Requesting a Model or Schema Change

Feature teams (G01–G16) do not modify `schema.prisma` or generate migrations directly. To request a new table, column, or relation:

1. **Document Requirements:** Specify your entity requirements in `db/schema-docs/<module>.md` (listing fields, data types, nullability, relationships with other modules, indexes, and query patterns).
2. **Submit Schema Request:** Open a PR or issue targeting the Database Leads with your updated `db/schema-docs/<module>.md`.
3. **DB Team Implementation:** The DB Leads translate the domain requirements into normalized tables in `db/prisma/schema.prisma`, apply naming conventions, configure constraints, and execute the migration (`npx prisma migrate dev --schema=db/prisma/schema.prisma --name <team_id>_<description>`).
4. **Client Update:** Once the migration PR is merged into `dev`, feature teams pull the latest branch and run `npx prisma generate --schema=db/prisma/schema.prisma` to update the generated Prisma client types.

## Table naming

**No module prefix on table/model names** — names should read like plain domain entities, not be namespaced by team or module:

```
Reservation
SeatHold
RefundLedger
CrewPairing
```

Prisma model names are PascalCase by convention; the underlying Postgres table name is set explicitly with `@@map(...)`, snake_case equivalent (`reservations`, `seat_holds`, `refund_ledger`, `crew_pairings`).

**Collision risk is real without a prefix.** Before requesting a new model in `schema-docs/`, search `schema.prisma` for an existing name or close to it (`Reservation` vs `Booking`, `Ticket` vs `Fare`, etc.) — DB leads are the backstop catching this in review, but check first rather than relying on them to catch it every time.

## Rules

1. **Only the Database Team writes Prisma models and executes migrations.** Direct modifications to `db/prisma/schema.prisma` or `db/prisma/migrations/` from feature teams will be rejected in code review.

2. **Migrations are append-only and machine-generated by DB Leads.** Never hand-edit, rename, or delete existing migration files. Corrective changes are implemented via forward migrations by the DB Team.

3. **Cross-module relations (foreign keys) require coordination between involved teams and DB Leads.** If `Reservation` needs a relation to `PassengerProfile`, both feature teams and the DB Leads must align on the contract before implementation.

4. **No shared "god models."** Each module owns its own data. If two modules seem to need the same table, that is a design indicator that domain boundaries need re-evaluation with DB Leads.

5. **`schema-docs/<module>.md` is mandatory for every module.** This document specifies what data tables your module requires, domain definitions for each field, and business rules.

6. **`ERD.md` is updated by DB Leads.** DB Leads maintain the system-wide entity relationship diagram at major milestones and contract-freeze points.

## Schema Governance & Review

- All changes to `/db/prisma/` originate from and are reviewed by the Database Leads.
- If a requested schema update introduces a cross-module relation or impact, the affected feature team leads must sign off on the design in `db/schema-docs/<module>.md`.
- `/db/` is protected in `.github/CODEOWNERS` under `@CSC290-2026-AIRLINE/database-leads`.
