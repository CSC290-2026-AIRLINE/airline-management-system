## Overview

Feature 12 is the onboard shop. Customers browse a catalog of meals, snacks, drinks and duty-free products for their booked flight, order and pay for them through Feature 5, and catering staff manage the catalog, the catering order for each flight, and stock in the warehouse and on the aircraft. It has three actors:

- **Customer** — browses the menu, orders a meal for each passenger and other products for the booking, pays through F5, and cancels until the order window closes.
- **Staff** (catering role) — maintains products, prices and offerings, reviews and loads the catering order for a flight, and manages warehouse and flight stock.
- **System** — at the order cutoff, a scheduled job reads the F1 simulation clock, generates the catering order from paid orders and checks it against stock.

Decisions, revised 2026-10-08 after feedback (the first three replace the 2026-09-30 decisions):

| Topic | Decision |
| --- | --- |
| Payment | Orders are priced and paid through F5 checkout. Prices live in the product catalog, F12 sends F5 the order total, and F5 owns the payment and any refund. Replaces "free, no F5 call". |
| Order window | Customers can order up to 2 days (48 hours) before departure on the F1 simulation clock. The default is 48 hours, set per cabin in cabin\_setting. Replaces the 24-hour cutoff. |
| Catalog scope | One catalog with four categories: meal, snack, beverage and duty\_free. Duty-free is ordered in advance within the same window and collected on board. Replaces "duty-free out of scope". |
| Special meals | Unchanged: meals identified by a type code (`VGML`, `MOML`, `KSML`, `DBML`, `GFML`) in the same catalog, one order path for regular and special meals. |
| Tier benefit | Tier holders get meals free of charge. Premium meals, snacks, drinks and duty-free are charged at full price. Tier is read from F11 at order time. |
| Stock | Two levels: warehouse stock (one warehouse per departure airport) and flight stock (loaded on the aircraft). An order is accepted only if available warehouse stock (on hand minus reserved) covers it. Replaces "no stock management". |

**Added 2026-10-09** from the mini devs' inventory spec: customers add meals as an optional extra service (the spec's "choose on board" still works for anyone who skips it); each flight has a Complimentary or Paid meal policy and its own menu; stock is tracked by supplier batch with expiry, moved to the aircraft by transfer, and updated from a flight-level report. Full meals left over after a flight are discarded; sealed snacks that are still valid stay on the aircraft.

Added 2026-10-11: (7) products carry a photo that customers see on the menu card, so staff upload it in the Product Catalog.

Revised 2026-10-12 after the schema review: (1) one cabin\_setting table and one product\_offering table, each with a network, route or flight scope, replace flight\_meal\_policy and flight\_menu\_item; (2) the catering order is generated at the scheduled departure minus the shortest cabin window, so a delay cannot move the cutoff; (3) stock\_movement changes one place per row (a warehouse or an aircraft), is append-only, and cannot record a retried reserve or release twice; (4) an unpaid order expires at the earlier of its hold and the cutoff, and payment events are safe to receive twice; (5) a line records why its price is what it is (price\_basis), product\_sale keeps the unit cost, and stock\_batch has is\_damaged; (6) included\_per\_passenger is 0 or 1, staff record on-board sales after the flight at flight level, F11 serves the tier, and flight codes use FL.

Authentication follows the platform pattern from Feature 7 (Clerk OAuth, backend-issued JWT). It is out of scope for this feature's diagram and UI.

## Data model

Twenty-one tables carry Feature 12's data, all named in the singular. `booking_id`, `booking_passenger_id` and `payment_id` are plain UUID columns with no foreign key, because the F3b and F5 schemas do not exist yet and those ids are validated through their APIs. `route_id`, `flight_id`, `aircraft_id` and `airport_code` point to F2 and F9 tables that are never hard-deleted, so the optional cross-module script (decision D6) adds their foreign keys.

| Table | Key columns | Notes |
| --- | --- | --- |
| `product` | `sku`, `category`, `type_code`, `name`, `price_amount`, `purchase_cost_amount`, `shelf_life_days`, `is_premium`, `is_active`, `image_key` | The catalog, priced in the base currency (F4's USD), so there is no currency column. `category` is `meal`, `snack`, `beverage` or `duty_free`. `type_code` is `STD` or a special-meal code, meals only. `image_key` points to the product photo in object storage; it is null when no photo has been uploaded, and the shop then shows a placeholder. |
| `product_offering` | `product_id` (FK), `scope`, `route_id`, `flight_id`, `cabin`, `is_default` | Which product is sold at which level (network, route or flight) and cabin. The most specific level with any row for a cabin replaces the others as a whole. Premium economy follows the economy menu, so it has no rows of its own. One default meal per level and cabin. |
| `product_order` | `customer_id` (FK), `booking_id`, `flight_id`, `cabin`, `status`, `total_amount`, `currency`, `payment_id`, `paid_at`, `expires_at`, `cancelled_at` | One row per checkout. Status is `pending_payment`, `confirmed`, `cancelled` or `expired`. `payment_id` is unique, so a repeated payment event cannot attach one payment to two orders. `expires_at` is never later than the cutoff. |
| `product_order_line` | `product_order_id` (FK), `flight_id`, `product_id`, `category`, `booking_passenger_id`, `quantity`, `unit_price_amount`, `price_basis` | Price snapshot per line. `price_basis` is `standard`, `tier_benefit` or `included`; the last two cost 0. A meal line names its passenger; at most one active meal per passenger per flight. Flight and category are copies held by composite foreign keys. |
| `catering_order` | `flight_id`, `warehouse_id` (FK), `status`, `cutoff_at`, `generated_at`, `generated_by_staff_id` (FK, null when the job ran it) | One row per flight. Status is `generated`, `loaded`, `closed` or `void`. `cutoff_at` is the scheduled departure minus the shortest cabin order window. |
| `catering_order_line` | `catering_order_id` (FK), `cabin`, `product_id` (FK), `quantity_required`, `quantity_short`, `source` | Required quantity per cabin and product. `source` is `order` or `default`. |
| `warehouse` | `code`, `name`, `airport_code` | One warehouse per departure airport, enforced by a unique index. |
| `warehouse_stock` | `warehouse_id` (FK), `product_id` (FK), `quantity_on_hand`, `quantity_reserved`, `reorder_level` | Available = on hand minus reserved. On hand always equals the sum of the warehouse's batches; both change in one transaction. |
| `aircraft_stock` | `aircraft_id`, `product_id`, `stock_batch_id` (FK), `quantity` | What is on the aircraft, by batch. It replaces the earlier flight-level stock table and carries over between flights. The expiry is the batch's expiry, read by a join. |
| `stock_movement` | `product_id` (FK), `warehouse_id` or `aircraft_id`, `stock_batch_id`, `stock_transfer_id`, `product_order_id`, `flight_id`, `type`, `quantity`, `reason`, `note`, `created_by_staff_id` (FK), `occurred_at` | Append-only ledger of every stock change. Each row changes one place; a transfer is two rows. Types: receive, reserve, release, transfer, discard, adjust. Reasons: spoilage, damage, expired, count\_correction. A retried reserve or release cannot be recorded twice. |

**Deliberately excluded from scope:** in-flight crew point-of-sale (staff record on-board sales after the flight, at flight level), refund rules (F5 owns them), allergen tracking, and a second tier benefit.

Table names from Feature 7 (`customer`, `staff`) are referenced as written in its data model; its SQL block currently uses plural names and should be aligned to singular.

## Inventory, purchasing and flight policy

This section merges the mini devs' inventory spec (Group 15, "Onboard Products and Inventory Management") into the shop above. The stock chain is now Supplier, then warehouse batch, then aircraft, then flight report. Customers can still add meals and other products as extra services before the cutoff. Stock and sales on board are reported per flight, never per passenger.

**How the two sources fit together**

| Mini devs' spec | This design |
| --- | --- |
| Customers do not pick a meal at booking; they choose on board | Pre-ordering a meal is an optional extra service. A passenger who orders nothing still gets the flight's included meal (complimentary flights) or buys on board (paid flights). |
| Each flight is Complimentary or Paid, with its own menu | Replaced by one cabin\_setting table and one product\_offering table, each with a network, route or flight scope. The most specific level that has any row for a cabin replaces the other levels as a whole. |
| Sales and usage are flight-level, with no passenger identity | Pre-orders stay in product\_order because payment and refunds need the customer. On-board sales go in product\_sale with no passenger. Reports add both. |
| Purchase cost and selling price are separate | Added: product.purchase\_cost\_amount, plus the real unit cost on each stock\_batch. Margin = selling price minus batch cost; product\_sale keeps the unit cost, filled when the flight report is submitted. |
| Stock is tracked by batch with its own expiry | Added: supplier, purchase\_receipt and stock\_batch. warehouse\_stock keeps the totals, and on hand is the sum of its batches. |
| Aircraft stock is separate from the warehouse | Added: stock\_transfer and aircraft\_stock. This replaces flight\_stock. |
| Staff submit a flight-level report | Added: flight\_report. The report drives the completion rules below. |
| Dietary attributes are not categories | Added: product\_dietary (halal, vegetarian and others). type\_code stays for special-meal ordering. |

**New tables**

| Table | Key columns | Notes |
| --- | --- | --- |
| `supplier` | `name`, `airport_code`, `contact`, `is_active` | An airport can have several suppliers. |
| `purchase_receipt` | `supplier_id` (FK), `warehouse_id` (FK), `received_at`, `received_by_staff_id` (FK) | One row per delivery. The delivery total is the sum of its batches, not a stored column. |
| `stock_batch` | `purchase_receipt_id` (FK), `warehouse_id` (FK), `product_id` (FK), `batch_code`, `quantity_received`, `quantity_remaining`, `unit_cost_amount`, `received_at`, `expires_at`, `is_damaged` | Expiry is per batch. `expires_at` is null for duty-free. Damaged batches are never transferred. |
| `product_dietary` | `product_id` (FK), `attribute` | Many rows per product. Closed list: halal, vegetarian, vegan, kosher, diabetic, gluten\_free (the owner finishes it). |
| `cabin_setting` | `scope`, `route_id`, `flight_id`, `cabin`, `meal_service`, `meal_selection`, `included_per_passenger`, `preorder_enabled`, `order_window_hours`, `premium_meals_allowed`, `snacks_enabled`, `duty_free_enabled`, `onboard_buffer_percent`, `updated_by_staff_id` (FK) | Settings by network, route or flight, per cabin. A NULL value inherits from the next level up. `meal_service = none` means no meal service. The network row for each cabin holds every value, and four network rows are seeded. It replaces flight\_meal\_policy. |
| `catering_setting` | `key`, `value`, `updated_by` (FK) | Closed list of keys. Today only `payment_hold_minutes` (default 30). |
| `stock_transfer` | `flight_id`, `aircraft_id`, `warehouse_id` (FK), `transferred_at`, `staff_id` (FK) | Warehouse to aircraft. This is a transfer, not a purchase. |
| `stock_transfer_line` | `stock_transfer_id` (FK), `stock_batch_id` (FK), `product_id` (FK), `quantity` | Which batch each unit came from. |
| `flight_report` | `flight_id`, `status`, `submitted_by_staff_id` (FK), `submitted_at` | One report per flight. |
| `flight_report_line` | `flight_report_id` (FK), `product_id` (FK), `initial_quantity`, `served`, `sold`, `wasted`, `damaged`, `remaining` | Flight totals per product. `sold` equals the flight's recorded on-board sales of that product. |
| `product_sale` | `flight_id`, `product_id` (FK), `quantity`, `unit_price_amount`, `unit_cost_amount`, `total_amount`, `currency`, `payment_id`, `sold_at` | One row per product per payment, recorded by staff after the flight at flight level. No passenger. Nothing is stored if F5 reports a failure. Unit cost is filled when the flight report is submitted. |

The catalog also gains purchase\_cost\_amount, shelf\_life\_days and image\_key on product. Stock tables are named in the singular as before.

**Pricing under a flight's meal policy**

- The policy is set per flight and cabin, so a budget economy fare can differ from business class on the same flight.
- Complimentary: the included meal (included\_per\_passenger, 0 or 1, default 1) costs 0. Extra food is charged.
- Paid: every meal is charged, and passengers buy it before the flight or on board.
- meal\_service = none means no meal service in that cabin, and the shop shows no meals and says so. A missing row means inherit from the next level up.
- Fixed selection: the passenger gets the set meal for that cabin and the meal picker is hidden. Special-meal codes (VGML, MOML and so on) can still be requested, because they are dietary needs, not a choice of dish.
- A tier holder still gets a free meal where meals are sold, and premium meals are always charged. A line has one price basis (standard, tier\_benefit or included), so the two free benefits never stack on one line.
- The booking screen states that extra food costs money, even on complimentary flights.

**Batches and expiry**

- Food (meal and snack) expires 2 days after it is received. This is the current project rule, stored as shelf\_life\_days so it can change.
- Beverages use their own shelf life per product. Duty-free has no expiry.
- Transfers take the earliest-expiring valid batch first. Expired or is\_damaged batches are never transferred (BATCH\_EXPIRED). A simulation-clock job writes expired batches off (adjust, reason expired), and a reservation only counts batches that are still valid at the flight's departure.

  Every airport has its own warehouse, stock and batches, and a flight is loaded at its departure airport. FL308 from Bangkok draws on the BKK warehouse, and FL309 back from Tokyo draws on the NRT warehouse, so each station has its own deliveries and shortfalls. Meals left on the aircraft are discarded; sealed snacks and duty-free stay on board and carry over to the next station while their batch is valid. Moving stock between airports is not part of Iteration-01.
- Snacks that stay on the aircraft are checked against their batch expiry before every later flight.

**Flight completion rules**

Staff submit the flight report. For each product, remaining = initial minus served, sold, wasted and damaged. sold is taken from the flight's recorded on-board sales (product\_sale) and cannot be typed in. A negative result is refused (REPORT\_MISMATCH).

| Product | What happens to the remaining quantity |
| --- | --- |
| Meal (full meal) | Discarded. Aircraft stock for that flight becomes 0, and a discard movement is recorded. |
| Snack (sealed) | Stays on the aircraft if its batch is still valid and it is not damaged. Otherwise discarded. |
| Beverage | Kept, as long as its batch is valid. |
| Duty-free | Kept. |

Catering planning changes with the policy. A complimentary flight plans the included meal for every passenger, with pre-orders choosing which meal. A paid flight plans pre-orders plus a buffer for on-board sales. The buffer percentage is an open question.

## Settings by route and cabin

How meals and extras work is configured, not hard-coded. Staff set it for each cabin, and can set it for the whole network, one route or one flight. The most specific setting wins, so most routes inherit and only the exceptions are written down.

**Order of precedence** (first match wins): the flight, then the route, then the network default. Three levels only; there are no route groups in Iteration-01. The same order resolves the menu in product\_offering: the most specific level that has any row for a cabin replaces the other levels as a whole, with no merging. A NULL setting inherits, and the network row for each cabin holds every value.

**Settings for each cabin**

| Setting | Values | What it controls |
| --- | --- | --- |
| meal\_service | complimentary, paid or none | Whether the meal is free, charged, or not offered in this cabin. |
| meal\_selection | choose or fixed | Whether passengers pick their meal or get the set one. |
| included\_per\_passenger | 0 or 1, default 1 | Meals that cost 0 on a complimentary cabin. |
| preorder\_enabled | on or off | Whether customers can order ahead in the shop. Off means on board only. |
| order\_window\_hours | whole number, default 48 | How long before departure ordering closes. The catering order is generated at the shortest window among the flight's cabins, and each order checks its own cabin's window. |
| premium\_meals\_allowed | on or off | Whether premium meals can be sold in this cabin. |
| snacks\_enabled, duty\_free\_enabled | on or off | Whether those categories appear in this cabin. |
| onboard\_buffer\_percent | whole number | Extra meals loaded for on-board sales on a paid cabin. |

This turns four of the open questions into settings: the free-meal allowance, the buffer percentage, the order window, and whether pre-ordering is allowed at all. The tier benefit stays in F11 and applies on top of these settings.

**How it resolves**

- The shop and the API read the resolved setting for the booking's flight and cabin. Nothing is copied onto the order except the price.
- A setting changed after customers have ordered does not rewrite their orders. It applies to new orders, and changing a cabin to none cancels nothing automatically; staff see a warning with the count of open orders.
- Product price changes, settings changes, flight overrides and stock adjustments are written through Feature 15's audit service (action update, source\_feature 12) with the staff member, a reason and the time.
- Route groups were dropped. If they return later, a level can be added between route and network without changing the settings below.

**Staff screen**

Offered menu is one page: a network default card, a routes table, and a table of single-flight exceptions. Route detail is where the rules and the menu are edited, for the whole route, a single flight or the network default. Each value is labelled Inherited or Custom, with Reset to inherited. Premium economy has its own rules but follows the economy menu in this iteration.

## Ordering, payment and stock lifecycle

The catering order is built from paid orders and checked against real stock, so the airline never promises food it does not have. Every time comparison uses the F1 simulation clock, not the system clock. Each flight uses the warehouse at its departure airport; F2 supplies the airport code. The cutoff uses the scheduled departure, so a delay or diversion does not move it, and an aircraft change from F2 flags the catering order for staff.

1. A booking is confirmed in F3b. The customer can then browse the menu for each flight on the booking and add products to a cart. A meal is chosen per passenger, at most one per passenger per flight; snacks, drinks and duty-free are chosen per booking.
2. Ordering is open until `cutoff_at`, the scheduled departure minus the cabin's order window (48 hours by default; the catering order uses the shortest window). After that the API returns `ORDER_WINDOW_CLOSED`.
3. At checkout the API validates the cart, prices each line, and checks available warehouse stock. Meals are free for tier holders, and free within the included allowance on a complimentary flight; premium meals, snacks, drinks and duty-free are charged. It creates the order as `pending_payment`, reserves the stock, and asks F5 to collect the total. A total of 0 skips F5 and confirms at once.
4. When F5 reports the payment as paid, the order becomes `confirmed`. If payment fails or the order is not paid before `expires_at`, it becomes `expired` and the reservation is released. expires\_at is the earlier of creation plus the hold (30 minutes by default, set in catering\_setting) and the cutoff. A payment reported after expires\_at does not confirm the order: the API returns PAYMENT\_AFTER\_EXPIRY and asks F5 to refund. Payment events are safe to receive twice.
5. A customer can cancel a confirmed order until the cutoff. The reservation is released and F5 is asked to refund. To change an order, the customer cancels it and orders again.
6. When the simulation clock passes `cutoff_at`, a scheduled job generates the `catering_order` for the flight by itself; staff do not press a button to create it. After the cutoff staff can refresh the order to recount it against current stock, for example after a delivery. Generation counts confirmed lines by cabin and product. On a complimentary flight it then adds the default meal for every passenger who ordered no meal. On a paid flight it adds a buffer for on-board sales instead.
7. Ordered quantities were reserved at checkout, so they are covered. Default-meal quantities are not reserved, so generation checks them against available stock and records any gap in `quantity_short`. Staff resolve a gap by receiving stock or changing the offering. Loading is blocked until no line is short.
8. Staff transfer the stock to the aircraft, recording a `stock_transfer`. Each unit comes from a warehouse batch, earliest expiry first, and expired batches are refused. On hand and reserved go down, and `aircraft_stock` goes up.
9. After the flight, staff submit the `flight_report` with served, sold, wasted and damaged quantities. The completion rules decide what happens to the remaining stock (meals discarded, valid snacks kept), and the catering order is `closed`. On-board sales are stored in `product_sale` once F5 confirms payment.
10. If F2 reports the flight cancelled, open orders are cancelled and refunded through F5, reservations are released, and the catering order becomes `void`.

Rules the API enforces:

| Rule | Error code |
| --- | --- |
| The booking belongs to the calling customer and is confirmed | `BOOKING_NOT_CONFIRMED` |
| Every product is on the flight's menu (flight menu, else route offerings) | `PRODUCT_NOT_OFFERED` |
| At most one meal per passenger per flight | `MEAL_LIMIT_EXCEEDED` |
| The order window is still open | `ORDER_WINDOW_CLOSED` |
| Available warehouse stock covers each line | `OUT_OF_STOCK` (details: product, available) |
| F5 accepted the payment | `PAYMENT_FAILED` |
| Refresh is called before the cutoff | `ORDER_NOT_YET_DUE` |
| Transfer is called while a line is still short | `STOCK_SHORTFALL` |
| A transferred batch is past its expiry or damaged | `BATCH_EXPIRED` |
| A flight report would leave a negative remaining quantity | `REPORT_MISMATCH` |
| A cabin setting has an invalid value or selection mode | `MEAL_POLICY_INVALID` |
| The passenger picks a meal where selection is fixed, or in a cabin with no meal service | `MEAL_CHOICE_NOT_ALLOWED` |
| The flight's departure airport has no warehouse | `NO_WAREHOUSE_FOR_AIRPORT` |
| A product with stock or open orders is deleted | `PRODUCT_IN_USE` |
| F5 reports a payment as paid after the order's expires\_at | `PAYMENT_AFTER_EXPIRY` |
| A cabin or catering setting value is invalid, for example included\_per\_passenger above 1 | `SETTING_INVALID` |

## Tier benefit and cross-module contracts

Feature 12 depends on six other modules and owns no shared data. Each contract below must be locked with its owning group by week 3–4.

| Module | F12 needs | How |
| --- | --- | --- |
| F1 Platform core | Verify JWTs, role check for staff (a catering role, agreed with F1 and F15), simulation clock | JWKS endpoint and the shared clock client helper. F12 never calls the real system clock. |

| F5 Payment | Collect an order total, learn the result, refund on cancel | Proposed: F12 sends reference (`product_order.id`), amount, currency and customer id; F5 returns `payment_id`; F5 reports paid or failed to `POST /payment-events`. Currency must match F5's. |
| F11 Loyalty | Customer tier | Read at order time. A missing or stale tier is treated as no tier and never blocks an order. |
| F15 Admin console | Audit entries for price changes, settings changes, flight overrides and stock adjustments | Call F15's audit service with action update, source\_feature 12 and a mandatory reason. Lock the contract with the F15 owner. |

The tier benefit works like this: a customer with a tier pays 0 for meals. The line stores `unit_price_amount = 0` and `price_basis = tier_benefit`, so a later tier or price change does not rewrite history. Premium meals (`is_premium`), snacks, drinks and duty-free are charged at full price.

This replaces the earlier reading of the benefit as "premium meals unlocked for tier members". With priced orders the plain reading of a free meal fits better.

Feature 7's own data model excluded the tier field, so F12 must not read it from `customer`. F11 serves the tier: it calculates it and pushes it to F12, and F7 only stores it for display.

F12 is not on the `/work-queue` list (3b, 8, 10, 13, 15), so it builds no work-queue screen or endpoint.

## SQL

```sql
-- Feature 12 (Onboard Products), reviewed schema, 21 tables, all singular.
-- Settings resolution (flight, route, network), completion rules, earliest-expiry transfers, the order and payment state
-- machine and on-hand reconciliation are backend logic, each with a test.
-- Uses customer (feature 7), staff (feature 1) and forbid_mutation() (baseline). Needs PostgreSQL 15+ (NULLS NOT DISTINCT).
-- booking_id, booking_passenger_id and payment_id belong to features 3b and 5, whose schemas do not exist yet: no foreign key.
-- The route, flight, aircraft and airport foreign keys are in the cross-module script below.
-- Business timestamps (generated_at, transferred_at, submitted_at, sold_at, occurred_at, expires_at) have no default and
-- come from the F1 simulation clock. created_at and updated_at are real time.
-- Money is NUMERIC in the base currency (feature 4, pricing_setting 'base_currency'). Orders and sales keep a currency snapshot.

-- Catalog ---------------------------------------------------------------------------------------------

-- Products are priced in the base currency: there is no per-product currency column.
-- shelf_life_days is set for everything except duty-free (food 2 days today, beverages per product).
CREATE TABLE product (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sku                  TEXT NOT NULL,
  category             TEXT NOT NULL CHECK (category IN ('meal', 'snack', 'beverage', 'duty_free')),
  type_code            TEXT NOT NULL DEFAULT 'STD' CHECK (type_code IN ('STD', 'VGML', 'MOML', 'KSML', 'DBML', 'GFML')),
  name                 TEXT NOT NULL,
  description          TEXT,
  price_amount         NUMERIC(12, 2) NOT NULL CHECK (price_amount >= 0),
  purchase_cost_amount NUMERIC(12, 2) CHECK (purchase_cost_amount >= 0),
  shelf_life_days      INTEGER CHECK (shelf_life_days > 0),
  is_premium           BOOLEAN NOT NULL DEFAULT false,         -- premium meals are outside the tier benefit
  is_active            BOOLEAN NOT NULL DEFAULT true,
  image_key            TEXT,                                   -- object storage key; NULL = placeholder photo
  image_updated_at     TIMESTAMPTZ,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at           TIMESTAMPTZ,
  CHECK (category = 'meal' OR type_code = 'STD'),
  CHECK ((category = 'duty_free') = (shelf_life_days IS NULL)),
  UNIQUE (id, category)                                        -- lets order lines carry a category that cannot drift
);

CREATE UNIQUE INDEX product_sku_uq ON product (sku) WHERE deleted_at IS NULL;

-- The list is a proposal: the owner finishes it. VGML = vegetarian, MOML = halal, KSML = kosher, DBML = diabetic, GFML = gluten free.
CREATE TABLE product_dietary (
  product_id UUID NOT NULL REFERENCES product (id),
  attribute  TEXT NOT NULL CHECK (attribute IN ('halal', 'vegetarian', 'vegan', 'kosher', 'diabetic', 'gluten_free')),
  PRIMARY KEY (product_id, attribute)
);

-- One menu table for all three levels. The most specific level that has any row for a cabin replaces the less specific
-- ones as a whole (it is not merged); premium_economy follows the economy menu in the backend, so it has no rows here.
-- The default meal must be a meal: the backend checks it.
CREATE TABLE product_offering (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id UUID NOT NULL REFERENCES product (id),
  scope      TEXT NOT NULL CHECK (scope IN ('network', 'route', 'flight')),
  route_id   UUID,                                             -- feature 2's route (cross-module FK)
  flight_id  UUID,                                             -- feature 2's flight (cross-module FK)
  cabin      TEXT NOT NULL CHECK (cabin IN ('economy', 'business', 'first')),
  is_default BOOLEAN NOT NULL DEFAULT false,                   -- the meal for passengers who order none
  is_active  BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ,
  CHECK ((scope = 'network' AND route_id IS NULL AND flight_id IS NULL)
      OR (scope = 'route'   AND route_id IS NOT NULL AND flight_id IS NULL)
      OR (scope = 'flight'  AND flight_id IS NOT NULL AND route_id IS NULL))
);

CREATE UNIQUE INDEX product_offering_uq
  ON product_offering (product_id, route_id, flight_id, cabin) NULLS NOT DISTINCT WHERE deleted_at IS NULL;
-- At most one default meal per level and cabin.
CREATE UNIQUE INDEX product_offering_default_uq
  ON product_offering (route_id, flight_id, cabin) NULLS NOT DISTINCT WHERE is_default AND deleted_at IS NULL;

-- Settings by network, route and flight, per cabin. A NULL value means inherit from the next level up.
-- The network row for a cabin holds every value, so resolution always ends. Replaces flight_meal_policy:
-- meal_service = 'none' is "no meal service", and a missing flight row means inherit.
-- included_per_passenger is 0 or 1 because a passenger can order at most one meal per flight; the backend treats it as 0
-- unless the resolved meal_service is 'complimentary'.
CREATE TABLE cabin_setting (
  id                     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  scope                  TEXT NOT NULL CHECK (scope IN ('network', 'route', 'flight')),
  route_id               UUID,                                 -- feature 2's route (cross-module FK)
  flight_id              UUID,                                 -- feature 2's flight (cross-module FK)
  cabin                  TEXT NOT NULL CHECK (cabin IN ('economy', 'premium_economy', 'business', 'first')),
  meal_service           TEXT CHECK (meal_service IN ('complimentary', 'paid', 'none')),
  meal_selection         TEXT CHECK (meal_selection IN ('choose', 'fixed')),
  included_per_passenger INTEGER CHECK (included_per_passenger BETWEEN 0 AND 1),
  preorder_enabled       BOOLEAN,
  order_window_hours     INTEGER CHECK (order_window_hours >= 0),
  premium_meals_allowed  BOOLEAN,
  snacks_enabled         BOOLEAN,
  duty_free_enabled      BOOLEAN,
  onboard_buffer_percent INTEGER CHECK (onboard_buffer_percent BETWEEN 0 AND 100),
  updated_by_staff_id    UUID REFERENCES staff (id),
  updated_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK ((scope = 'network' AND route_id IS NULL AND flight_id IS NULL)
      OR (scope = 'route'   AND route_id IS NOT NULL AND flight_id IS NULL)
      OR (scope = 'flight'  AND flight_id IS NOT NULL AND route_id IS NULL)),
  CHECK (scope <> 'network' OR (meal_service IS NOT NULL AND meal_selection IS NOT NULL AND included_per_passenger IS NOT NULL
         AND preorder_enabled IS NOT NULL AND order_window_hours IS NOT NULL AND premium_meals_allowed IS NOT NULL
         AND snacks_enabled IS NOT NULL AND duty_free_enabled IS NOT NULL AND onboard_buffer_percent IS NOT NULL))
);

CREATE UNIQUE INDEX cabin_setting_uq ON cabin_setting (route_id, flight_id, cabin) NULLS NOT DISTINCT;

-- Closed list of keys. Values are validated by the backend.
CREATE TABLE catering_setting (
  key        TEXT PRIMARY KEY CHECK (key IN ('payment_hold_minutes')),
  value      TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by UUID REFERENCES staff (id)

-- Customer orders ---------------------------------------------------------------------------------------

CREATE TABLE product_order (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id  UUID NOT NULL REFERENCES customer (id),
  booking_id   UUID NOT NULL,                                  -- feature 3b
  flight_id    UUID NOT NULL,                                  -- feature 2's flight (cross-module FK)
  cabin        TEXT NOT NULL CHECK (cabin IN ('economy', 'premium_economy', 'business', 'first')),
  status       TEXT NOT NULL DEFAULT 'pending_payment' CHECK (status IN ('pending_payment', 'confirmed', 'cancelled', 'expired')),
  total_amount NUMERIC(12, 2) NOT NULL CHECK (total_amount >= 0),
  currency     TEXT NOT NULL,                                  -- base currency when ordered
  payment_id   UUID,                                           -- feature 5; NULL when the total is 0
  paid_at      TIMESTAMPTZ,                                    -- simulation clock
  expires_at   TIMESTAMPTZ NOT NULL,                           -- simulation clock; never later than the cutoff
  cancelled_at TIMESTAMPTZ,                                    -- simulation clock
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, flight_id)
);

-- A repeated payment event cannot attach one payment to two orders.
CREATE UNIQUE INDEX product_order_payment_uq ON product_order (payment_id) WHERE payment_id IS NOT NULL;
CREATE INDEX product_order_booking_idx ON product_order (booking_id);
CREATE INDEX product_order_customer_idx ON product_order (customer_id);
CREATE INDEX product_order_flight_idx ON product_order (flight_id, status);

-- Flight and category are copies, kept honest by composite foreign keys, so the one-meal rule below cannot be bypassed.
-- deleted_at is set in the same transaction as the order's change to cancelled or expired (the backend, with a test).
-- price_basis says why the price is what it is: 'standard' is the product price, 'tier_benefit' and 'included' are free.
CREATE TABLE product_order_line (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_order_id     UUID NOT NULL,
  flight_id            UUID NOT NULL,
  product_id           UUID NOT NULL,
  category             TEXT NOT NULL,
  booking_passenger_id UUID,                                   -- feature 3b; set on meal lines only
  quantity             INTEGER NOT NULL CHECK (quantity > 0),
  unit_price_amount    NUMERIC(12, 2) NOT NULL CHECK (unit_price_amount >= 0),
  price_basis          TEXT NOT NULL DEFAULT 'standard' CHECK (price_basis IN ('standard', 'tier_benefit', 'included')),
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at           TIMESTAMPTZ,
  FOREIGN KEY (product_order_id, flight_id) REFERENCES product_order (id, flight_id),
  FOREIGN KEY (product_id, category) REFERENCES product (id, category),
  CHECK ((category = 'meal') = (booking_passenger_id IS NOT NULL)),
  CHECK (category <> 'meal' OR quantity = 1),
  CHECK (price_basis = 'standard' OR unit_price_amount = 0)
);

-- One active meal per passenger per flight.
CREATE UNIQUE INDEX product_order_line_meal_uq
  ON product_order_line (booking_passenger_id, flight_id) WHERE category = 'meal' AND deleted_at IS NULL;
CREATE INDEX product_order_line_order_idx ON product_order_line (product_order_id);

-- Warehouses, suppliers and batches ---------------------------------------------------------------------

CREATE TABLE warehouse (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  code         TEXT NOT NULL UNIQUE,
  name         TEXT NOT NULL,
  airport_code TEXT NOT NULL,                                  -- feature 2's airport (cross-module FK)
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at   TIMESTAMPTZ
);

-- One warehouse per departure airport.
CREATE UNIQUE INDEX warehouse_airport_uq ON warehouse (airport_code) WHERE deleted_at IS NULL;

CREATE TABLE supplier (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name         TEXT NOT NULL,
  airport_code TEXT NOT NULL,                                  -- feature 2's airport (cross-module FK)
  contact      TEXT,
  is_active    BOOLEAN NOT NULL DEFAULT true,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at   TIMESTAMPTZ
);

-- The delivery total is the sum of its batches (quantity_received * unit_cost_amount), not a stored column.
CREATE TABLE purchase_receipt (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  supplier_id          UUID NOT NULL REFERENCES supplier (id),
  warehouse_id         UUID NOT NULL REFERENCES warehouse (id),
  received_at          TIMESTAMPTZ NOT NULL,                   -- simulation clock
  received_by_staff_id UUID NOT NULL REFERENCES staff (id),
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- quantity_on_hand is kept equal to the sum of the warehouse's batch quantity_remaining by the backend, in one transaction
-- with every change to a batch. quantity_reserved is the part of it promised to unpaid and confirmed orders.
CREATE TABLE warehouse_stock (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  warehouse_id      UUID NOT NULL REFERENCES warehouse (id),
  product_id        UUID NOT NULL REFERENCES product (id),
  quantity_on_hand  INTEGER NOT NULL DEFAULT 0 CHECK (quantity_on_hand >= 0),
  quantity_reserved INTEGER NOT NULL DEFAULT 0 CHECK (quantity_reserved >= 0),
  reorder_level     INTEGER NOT NULL DEFAULT 0 CHECK (reorder_level >= 0),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (warehouse_id, product_id),
  CHECK (quantity_reserved <= quantity_on_hand)                -- available = on hand - reserved
);

-- expires_at is NULL for duty-free only (the backend). is_damaged batches are never transferred.
CREATE TABLE stock_batch (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  purchase_receipt_id UUID NOT NULL REFERENCES purchase_receipt (id),
  warehouse_id        UUID NOT NULL REFERENCES warehouse (id),
  product_id          UUID NOT NULL REFERENCES product (id),
  batch_code          TEXT NOT NULL,
  quantity_received   INTEGER NOT NULL CHECK (quantity_received > 0),
  quantity_remaining  INTEGER NOT NULL CHECK (quantity_remaining >= 0),
  unit_cost_amount    NUMERIC(12, 2) NOT NULL CHECK (unit_cost_amount >= 0),
  received_at         TIMESTAMPTZ NOT NULL,                    -- simulation clock
  expires_at          TIMESTAMPTZ,                             -- received_at + shelf_life_days; NULL = no expiry
  is_damaged          BOOLEAN NOT NULL DEFAULT false,
  UNIQUE (warehouse_id, product_id, batch_code),
  UNIQUE (id, product_id),
  CHECK (quantity_remaining <= quantity_received)
);

-- Earliest-expiring first.
CREATE INDEX stock_batch_fefo_idx ON stock_batch (warehouse_id, product_id, expires_at) WHERE quantity_remaining > 0;

  cutoff_at             TIMESTAMPTZ NOT NULL,                  -- simulation clock

  product_id        UUID NOT NULL REFERENCES product (id),

  quantity_short    INTEGER NOT NULL DEFAULT 0 CHECK (quantity_short >= 0),

  wasted            INTEGER NOT NULL DEFAULT 0 CHECK (wasted >= 0),
  damaged           INTEGER NOT NULL DEFAULT 0 CHECK (damaged >= 0),
  remaining         INTEGER NOT NULL CHECK (remaining >= 0),
  UNIQUE (flight_report_id, product_id),
  CHECK (remaining = initial_quantity - served - sold - wasted - damaged)
);

-- Staff record these after the flight, at flight level (no point-of-sale).
-- One row per product per payment: a basket paid once is several rows with the same payment_id.
-- unit_cost_amount is the cost of the earliest-expiring aircraft batch, filled when the flight report is submitted.
-- No passenger column on purpose.
CREATE TABLE product_sale (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  flight_id         UUID NOT NULL,                             -- feature 2's flight (cross-module FK)
  product_id        UUID NOT NULL REFERENCES product (id),
  quantity          INTEGER NOT NULL CHECK (quantity > 0),
  unit_price_amount NUMERIC(12, 2) NOT NULL CHECK (unit_price_amount >= 0),
  unit_cost_amount  NUMERIC(12, 2) CHECK (unit_cost_amount >= 0),
  total_amount      NUMERIC(12, 2) NOT NULL CHECK (total_amount >= 0),
  currency          TEXT NOT NULL,
  payment_id        UUID NOT NULL,                             -- feature 5; stored only after it reports paid
  sold_at           TIMESTAMPTZ NOT NULL,                      -- simulation clock
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (payment_id, product_id),
  CHECK (total_amount = quantity * unit_price_amount)
);

CREATE INDEX product_sale_flight_idx ON product_sale (flight_id);

-- Stock ledger ---------------------------------------------------------------------------------------------

-- Append-only. Each row changes exactly one place: a warehouse or an aircraft. A transfer is two rows (minus at the
-- warehouse, plus on the aircraft) that share stock_transfer_id. quantity is signed. For reserve and release the row
-- changes quantity_reserved, not the stock itself. A retried reserve or release cannot be recorded twice.
CREATE TABLE stock_movement (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id          UUID NOT NULL REFERENCES product (id),
  warehouse_id        UUID REFERENCES warehouse (id),
  aircraft_id         UUID,                                    -- feature 9's aircraft (cross-module FK)
  stock_batch_id      UUID REFERENCES stock_batch (id),
  stock_transfer_id   UUID REFERENCES stock_transfer (id),
  product_order_id    UUID REFERENCES product_order (id),      -- reserve and release
  flight_id           UUID,                                    -- feature 2's flight (cross-module FK)
  type                TEXT NOT NULL CHECK (type IN ('receive', 'reserve', 'release', 'transfer', 'discard', 'adjust')),
  quantity            INTEGER NOT NULL CHECK (quantity <> 0),
  reason              TEXT CHECK (reason IN ('spoilage', 'damage', 'expired', 'count_correction')),
  note                TEXT,
  created_by_staff_id UUID REFERENCES staff (id),              -- NULL when the system made the change
  occurred_at         TIMESTAMPTZ NOT NULL,                    -- simulation clock
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (num_nonnulls(warehouse_id, aircraft_id) = 1),
  CHECK (type <> 'adjust' OR reason IS NOT NULL)
);

CREATE UNIQUE INDEX stock_movement_order_once_uq
  ON stock_movement (product_order_id, product_id, type) WHERE type IN ('reserve', 'release');
CREATE INDEX stock_movement_product_idx ON stock_movement (product_id, occurred_at);
CREATE INDEX stock_movement_flight_idx ON stock_movement (flight_id) WHERE flight_id IS NOT NULL;

CREATE TRIGGER stock_movement_no_change
  BEFORE UPDATE OR DELETE ON stock_movement
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

CREATE TRIGGER stock_movement_no_truncate
  BEFORE TRUNCATE ON stock_movement
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
```
