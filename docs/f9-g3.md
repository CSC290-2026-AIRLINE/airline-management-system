# Feature 9 — Aircraft Management (Iteration-03)

Sep 28, 2026 · @Zayar

**Prototype:** an interactive mockup of the staff-web pages — [Feature 9 — Aircraft Management Prototype](https://claude.ai/artifact/KhV38rkQcPjXmsbeNLRcVw).

## Overview

Feature 9 owns the fleet: which aircraft exist, how their cabins are laid out, whether each one can fly, and how much it can carry. It is staff-only. Passengers never touch it and only see the aircraft type on their itinerary. It has one actor:

- **Staff (admin)** — maintain the fleet registry, define aircraft types with their seat map, schedule maintenance and weekday availability, track turnaround, and mark aircraft status (in service / grounded / in maintenance) with a reason and date range.

Other modules use Feature 9 as a data source. Feature 2 reads availability (with the reason an aircraft is blocked), turnaround readiness, the reserve check, and each type's turnaround minutes, range, maximum takeoff weight and operating cost per hour, before assigning an aircraft to a flight. Features 3a and 8 read aircraft types (type name, type ratings). Features 3b and 6 read the seat map. Features 10 and 17 read the hold weight limit.

Authentication follows Feature 7's pattern (Clerk OAuth on staff-web, exchanged for the backend's own JWT), so it is not repeated here. Every route in this feature requires the admin role, the only staff role, except the read-only seat map and capacity routes, which a customer token may also call.

## Data model

Eight tables carry Feature 9's data, all named in the singular. Aircraft types hold the seat map (a JSON `layout` column), the hold weight limit, turnaround time and operating cost. Individual aircraft (by tail number) hold status, maintenance windows, operating days and turnarounds. A settings table holds the reserve ratio. Airport fees are not stored here; they belong to Feature 2's airport data. Every aircraft of a type shares that type's seat map. Total seat capacity is counted from the layout, not stored.

| Table | Key columns | Notes |
| --- | --- | --- |
| `aircraft_type` | code (unique among live types), manufacturer, model, layout (JSONB, set at creation), hold\_weight\_limit\_kg, max\_takeoff\_weight\_kg, max\_range\_km, min\_turnaround\_minutes, operating\_cost\_per\_hour, cost\_currency, is\_active | One row per type; layout is the seat map, set when the type is created and never changed (to change it, clone the type under a new code). Features 10 and 17 read the hold weight limit; Feature 2 reads turnaround minutes, range, maximum takeoff weight and cost per hour |
| `aircraft` | tail\_number (unique among live aircraft), aircraft\_type\_id (FK), entry\_into\_service\_date, retired\_on (nullable), base\_airport\_code | One row per physical aircraft; tail\_number is the registration. No status column, status lives in its own table |
| `aircraft_status_period` | aircraft\_id (FK), status, origin (manual or maintenance), reason, start\_date, end\_date (nullable) | Status is a date range, so history is kept, and periods never overlap. end\_date is the last unavailable day (inclusive). A new period that starts inside an open-ended one closes it the day before. Periods with origin maintenance belong to a maintenance window and change only through it. "Current status" is a lookup at the simulated date |
| `aircraft_maintenance` | aircraft\_id (FK), maintenance\_type, planned\_start\_date, planned\_end\_date, actual\_end\_date (nullable), status, status\_period\_id (FK) | Planned inspection window; planned\_end\_date is the last day the aircraft is unavailable. Creating one also creates its in\_maintenance status period (origin maintenance). A completed window must have an actual\_end\_date |
| `aircraft_operating_day` | aircraft\_id (FK), day\_of\_week (1 to 7) | One row per weekday the aircraft may fly; no rows means every day |
| `aircraft_turnaround` | aircraft\_id (FK), flight\_id (Feature 2's, no FK), airport\_code, arrived\_at | One per flight (unique on flight\_id). Readiness is derived from the tasks, not stored |
| `aircraft_turnaround_task` | turnaround\_id (FK), task\_type (refuel, cleaning, catering, inspection), status (pending, in\_progress, completed, skipped), started\_at, completed\_at | Ground activities; skipped counts as done. The turnaround is ready when it has tasks and all are completed or skipped, and ready\_at is the last completion time |
| `fleet_setting` | key (reserve\_ratio), value, updated\_at, updated\_by | Feature 9's own setting. reserve\_ratio is 1.00 to 9.99, default 1.10, validated by the backend |

**Capacity is derived, not stored.** Seats per cabin is computed by the backend from the type's `layout`, excluding blocked seats. Hold weight comes from `aircraft_type`. "Current" status is always evaluated against the shared simulation clock from Feature 1, never the real system clock.

**Deliberately excluded from scope:** flight-hour and cycle counters and the "next check due" flag derived from them (stretch), maintenance work orders and parts inventory, crew costs, airport fees and the flight cost estimate (both Feature 2's), and passenger-facing screens. Feature 9 plans maintenance windows but does not manage the repair work itself.

## Seat map layout JSON

The `layout` column on `aircraft_type` describes each cabin as rules, not as a list of seats. The backend expands the rules into a seat grid whenever another feature asks for it. The column is set when the aircraft type is created and never changes, so to change a layout, create a new aircraft type.

```json
{
  "cabins": [
    {
      "cabin_class": "business",
      "first_row": 1,
      "last_row": 4,
      "columns": ["A", "C", "D", "F"],
      "aisle_after": ["C"]
    },
    {
      "cabin_class": "economy",
      "first_row": 5,
      "last_row": 30,
      "columns": ["A", "B", "C", "D", "E", "F"],
      "aisle_after": ["C"],
      "skip_rows": [13],
      "row_types": {
        "extra_legroom": [5],
        "exit_row": [12, 14]
      },
      "blocked_seats": ["30F"]
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `cabin_class`, `first_row`, `last_row` | The cabin (for example first, business, economy) and the rows it covers |
| `columns` | Seat letters in each row; letters left out (B and E in business) are not seats |
| `aisle_after` | Letters after which an aisle runs (`C` means the aisle sits between C and D); used to draw the grid |
| `skip_rows` | Row numbers that do not exist (for example row 13) |
| `row_types` | Rows whose seats are not normal; anything not listed defaults to normal |
| `blocked_seats` | Individual seats that exist but are never sold, such as a crew rest seat |

Expansion: for each cabin, for each row from `first_row` to `last_row` (minus `skip_rows`), for each letter in `columns`, produce one seat. The example describes 16 business and 150 economy seats, of which 30F is blocked. The backend validates this JSON before saving, since Postgres does not check its shape: cabin\_class comes from the shared list; first\_row is not greater than last\_row and cabins do not overlap; columns are distinct capital letters; aisle\_after letters are among the columns; skip\_rows, row\_types and blocked\_seats lie inside the cabin and agree with each other. Because the layout never changes, the expanded grid is cached by aircraft\_type\_id.

**Response of `GET /aircraft/:id/seat-map`.** The backend returns each cabin with its columns and aisle positions, plus the expanded seat list, so Feature 6 can draw the grid without reading the raw layout. Blocked seats are included with `seat_type: "blocked"`. It returns `404` if the aircraft does not exist.

```json
{
  "aircraft_id": "...",
  "aircraft_type_id": "...",
  "cabins": [
    { "cabin_class": "business", "columns": ["A", "C", "D", "F"], "aisle_after": ["C"] },
    { "cabin_class": "economy", "columns": ["A", "B", "C", "D", "E", "F"], "aisle_after": ["C"] }
  ],
  "seats": [
    { "seat": "1A", "row": 1, "column": "A", "cabin_class": "business", "seat_type": "normal" },
    { "seat": "5A", "row": 5, "column": "A", "cabin_class": "economy", "seat_type": "extra_legroom" },
    { "seat": "12A", "row": 12, "column": "A", "cabin_class": "economy", "seat_type": "exit_row" },
    { "seat": "30F", "row": 30, "column": "F", "cabin_class": "economy", "seat_type": "blocked" }
  ]
}
```

## Seat map setup

An aircraft type's seat map is the `layout` JSON on `aircraft_type`. It is set when the type is created and treated as fixed afterwards. There is no versioning and no separate seat table, and every aircraft of that type shares the same map.

1. Staff enters the type's code, model and hold weight limit.
2. In the seat map editor on the same screen, staff adds each cabin (class, first and last row, seat letters, aisle position), marks special rows (exit row, extra legroom) and blocked seats.
3. Save calls `POST /aircraft-types`, which stores the type and its layout together. `PUT /aircraft-types/:id` can edit other fields but rejects any change to `layout`.
4. Features 3b and 6 call `GET /aircraft/:id/seat-map`, and the backend expands the type's layout into a grid.

A seat is blocked when it physically exists but is never sold, such as a crew rest seat or a bassinet position. Because the map belongs to the type, blocking applies to every aircraft of that type. Temporarily pulling a broken seat from sale is not modelled in Feature 9. Feature 3b builds its per-flight seat inventory from the expanded grid.

## Availability, maintenance and turnaround

Feature 2 may assign an aircraft to a flight only when these checks pass over the whole flight window: the aircraft is in the fleet (entered service, not retired), its status is in service on every day of the window, it operates on the departure weekday, and the flight's distance is within the type's `max_range_km`. Readiness after a turnaround applies only to the aircraft's imminent next departure; for later flights Feature 2 plans the gap from `min_turnaround_minutes` and the flight times. `GET /aircraft/:id/availability` names each failing check, and `GET /aircraft/available` applies the same checks to every aircraft of a type.

### Maintenance scheduling

Staff plans a maintenance window for an aircraft: the type of check (`a_check`, `b_check`, `c_check`, `d_check` or `unscheduled`), a planned start date and a planned end date. The planned end date is the last day the aircraft is unavailable; it is available again the next day. Saving the window creates its `in_maintenance` status period (origin `maintenance`) in the same transaction, so "current status" and the availability check read one source. A window that starts inside an open-ended period closes it the day before; a window that overlaps a period with an end date returns 409. The window is in progress from its planned start date on the simulation clock, with no staff action. Creating, rescheduling, completing and cancelling a window each update the window and its status period in one transaction. Staff completes a window with an actual end date, and the status period is shortened or extended to that date; a completed window must have one. If finishing late would overlap the next period, the completion is refused with 409 until staff moves that period.

### Operating days

`aircraft_operating_day` lists the weekdays an aircraft may fly, 1 for Monday to 7 for Sunday. An aircraft that only flies on Tuesday and Wednesday has rows 2 and 3. No rows means every day. A one-off unavailable date is not an operating-day rule; staff sets a status period instead. Saving the days replaces the whole set. The weekday is taken from the departure date at the origin airport's local time. Because no rows means every day, removing the last weekday makes the aircraft fly every day, and the screen says so.

### Turnaround

A turnaround starts once a flight has landed. Feature 2 has no landing event, so a job on the simulation clock starts a turnaround for each flight whose arrival time has passed, reading landed flights from Feature 2; the Start Turnaround button and `POST /aircraft/:id/turnarounds` do the same by hand. There is one turnaround per flight: starting it again returns the existing one, so retries are safe. Starting a turnaround creates the standard tasks (refuel, cleaning, catering, inspection) in the same transaction, and staff marks each task started, completed or skipped. A skipped task counts as done. Readiness is derived, not stored: the aircraft is ready when the turnaround has tasks and all are completed or skipped, and `ready_at` is the latest completion time. The type's `min_turnaround_minutes` is the planning figure Feature 2 uses before the flight lands; the task records are what actually happened. All times come from the simulation clock.

### Operating cost and profitability

Feature 9 stores one cost figure: `operating_cost_per_hour` (with `cost_currency`) on the aircraft type, entered when the type is created. Airport fees are not kept here. They are charges of an airport, so they live with Feature 2's airport master data, and Feature 2 owns the flight cost estimate: block hours times the type's `operating_cost_per_hour`, plus the fees at the origin and destination airports. Feature 2 compares the estimate with expected revenue from Features 3b and 4 and warns when a flight would run at a loss. Currency conversion uses Feature 4's currency table. Feature 9 knows neither ticket revenue nor airport fees.

### Reserve fleet rule

The fleet should hold about 10% more ready aircraft than it needs for a day. Aircraft needed is the number of distinct aircraft assigned to that day's flights; it is not the number of flights, because one aircraft flies several sectors a day. `GET /fleet/reserve` takes a date and `aircraft_needed` and returns the target (aircraft needed times the reserve ratio, rounded up), the number of aircraft ready, and the shortfall: `max(ceil(aircraft_needed x ratio) - ready, 0)`. Ready means in the fleet, in service, operating that weekday and not in maintenance. The ratio is the `reserve_ratio` row in `fleet_setting` (1.00 to 9.99, default 1.10). Feature 9 owns and edits it; Feature 15 is not involved.

## API routes

Guard label: S = staff (admin role), C = a customer token is also accepted. Every route is staff-only except the seat map and capacity reads, which accept S or C (Features 3b and 6 call them during booking and check-in) or an in-process call. Creates use POST, edits use PUT, and there is no PATCH. DELETE only cancels a status record entered by mistake. In Nest, declare `/aircraft/available` and `/aircraft/status-changes` before `/aircraft/:id`.

| Route | Method | Guard | Purpose | Returns |
| --- | --- | --- | --- | --- |
| `/aircraft-types` | GET | S | List aircraft types (including layout) | List of aircraft types |
| `/aircraft-types` | POST | S | Create an aircraft type (with hold weight limit, maximum takeoff weight and layout) | The created aircraft type; 400 if layout is invalid |
| `/aircraft-types/:id` | PUT | S | Edit an aircraft type, or retire it with is\_active (layout cannot be changed) | The updated aircraft type; 400 if layout changes |
| `/aircraft-types/:id/clone` | POST | S | Create a new type from an existing one with a new code and a new layout (the way to replace a wrong layout) | The created aircraft type; 409 if the code exists; 400 if layout is invalid |
| `/aircraft` | GET | S | List fleet (filter by type, base, status) | List of aircraft with current status |
| `/aircraft` | POST | S | Register an aircraft | The created aircraft |
| `/aircraft/:id` | GET | S | Aircraft detail with current status | The aircraft with its current status |
| `/aircraft/:id` | PUT | S | Edit registry fields, or retire the aircraft with retired\_on; the type cannot change once a flight uses the aircraft (409) | The updated aircraft |
| `/aircraft/:id/status` | GET | S | Current status at the simulated date | Status at the date; in\_service if none is set |
| `/aircraft/:id/status` | POST | S | Set a status period (in\_service or grounded only, with reason, start and end date; in\_maintenance comes only from a maintenance window and returns 400 here) | The created status period; an open-ended period it starts inside is closed the day before; 409 if it overlaps a period with an end date |
| `/aircraft/:id/status/:periodId` | DELETE | S | Cancel a status period entered by mistake (soft delete); a period created by a maintenance window changes only through the window | 204; 409 if the period belongs to a maintenance window |
| `/aircraft/:id/status/history` | GET | S | All status periods, newest first | List of status periods, newest first |
| `/aircraft/:id/seat-map` | GET | S | Cabins with aisle positions, plus the expanded seat list, for the aircraft's type | Cabins with aisle positions, plus the seat list (see Seat map layout JSON) |
| `/aircraft/:id/capacity` | GET | S | Seats per cabin and the hold weight limit | Seat counts per cabin and the hold weight limit (see below) |
| `/aircraft/available` | GET | S | Aircraft of a type that pass every availability check (query: type, from, to, dep\_date, distance\_km), for Feature 2 | List of available aircraft |
| `/aircraft/:id/availability` | GET | S | Availability of one aircraft (query: from, to, dep\_date, distance\_km); names each failing check | available flag and one row per failing check with its reason (see Response formats) |
| `/aircraft/status-changes` | GET | S | Aircraft whose status periods or maintenance windows changed since a simulated timestamp (query: since) | List of aircraft ids with the time of the change |
| `/aircraft/:id/maintenance` | GET | S | List maintenance windows | List of windows, newest first |
| `/aircraft/:id/maintenance` | POST | S | Schedule a maintenance window (type, planned start and end date) | The created window; 409 if it overlaps a status period with an end date |
| `/aircraft/:id/maintenance/:maintenanceId` | PUT | S | Reschedule, cancel, or complete with an actual end date | The updated window |
| `/aircraft/:id/operating-days` | GET | S | Weekdays the aircraft may fly | List of weekdays; empty means every day |
| `/aircraft/:id/operating-days` | PUT | S | Replace the whole set of weekdays | The saved list of weekdays |
| `/aircraft/:id/turnarounds` | POST | S | Start a turnaround for a landed flight (body: flight\_id, airport\_code, arrived\_at); returns the existing one if the flight already has one; creates the standard tasks | The turnaround with its tasks |
| `/aircraft/:id/turnarounds/latest` | GET | S | Latest turnaround and whether the aircraft is ready | Turnaround, its tasks, and a ready flag |
| `/turnarounds/:id/tasks/:taskId` | PUT | S | Mark a task started, completed or skipped | The updated task; readiness is recalculated from the tasks |
| `/fleet/reserve` | GET | S | Reserve check for a date and the aircraft needed (query: date, aircraft\_needed) | Target, ready count and shortfall |
| `/fleet/settings` | GET | S | Fleet settings (reserve\_ratio) | The settings object |
| `/fleet/settings/reserve_ratio` | PUT | S | Set the reserve ratio (1.00 to 9.99) | The saved value; 400 if out of range |

Error format is consistent across routes: `{ error: { code, message, details? } }`. Setting a status period that overlaps a period with an end date returns 409 with the conflicting period in details. A period that starts inside an open-ended one closes that one the day before instead.

## Cross-module contracts

Seven other features depend on Feature 9: 2, 3a, 3b, 6, 8, 10 and 17. Status changes reach Feature 2 by REST only, with no event stream. Feature 2 calls availability before it acts, and on each simulation clock step it asks `GET /aircraft/status-changes?since=` and re-checks the future flights of the aircraft listed, so a new grounding is noticed. These are the endpoints to lock by week 3–4.

| Consumer | Calls | Returns | Used for |
| --- | --- | --- | --- |
| Feature 2 (scheduling) | GET /aircraft/available, GET /aircraft/:id/availability, GET /aircraft/status-changes, GET /aircraft/:id/turnarounds/latest, GET /aircraft-types and GET /fleet/reserve | Available aircraft, with the failing check named; changed aircraft; turnaround readiness; type turnaround minutes, range, maximum takeoff weight and cost per hour; reserve shortfall | Checking an aircraft is flyable (and ready, for its next departure) before confirming an assignment, noticing new groundings, estimating flight cost with its own airport fees, and keeping about 10% reserve aircraft |
| Features 3a and 8 (search, crew) | GET /aircraft-types | Type code, manufacturer and model | Showing the aircraft type on an itinerary (3a) and matching crew type ratings (8) |
| Features 3b and 6 (booking, seat choice) | GET /aircraft/:id/seat-map (customer token or in-process call) | Seat grid with cabin and seat type | Seat inventory per flight and the clickable seat map |
| Feature 10 (baggage) | GET /aircraft/:id/capacity | hold\_weight\_limit\_kg | Proposed owner of the loaded weight per flight (its own bags plus the cargo weight reported by Feature 17); warns when it exceeds the limit |
| Feature 17 (cargo) | GET /aircraft/:id/capacity | hold\_weight\_limit\_kg | Reports cargo weight to Feature 10 instead of checking the limit alone, so baggage and cargo share one total |

**Audit:** Feature 9 sends an audit entry to Feature 15 for status periods, maintenance changes, cancellations and changes to the reserve ratio.

Staff is the only actor. Use cases are grouped into seven areas: fleet registry, aircraft types, seat map, aircraft status, maintenance and availability, turnaround, and the reserve check. There is no passenger-facing use case.

## Frontend pages

Minimum footprint: 4 pages, all in staff-web. Feature 9 is not on the shared `/work-queue` list, so it has no queue screen.

| App | Page | Contains |
| --- | --- | --- |
| staff-web | Fleet | Aircraft list with filters (type, base, status); detail panel with registry fields, current status, status history, maintenance windows and weekday toggles for operating days; Register Aircraft, Set Status and Schedule Maintenance modals; retire an aircraft; cancel a mistaken status record |
| staff-web | Aircraft Types | Aircraft types with total seats, hold weight limit, maximum takeoff weight, range, turnaround minutes and operating cost per hour; Clone Type and retire actions |
| staff-web | Seat Map Editor | Grid for the aircraft type being created; add each cabin (class, rows, letters, aisle position); mark whole rows as exit row or extra legroom; click a seat to block it; Save creates the aircraft type with this layout; capacity summary (seats per cabin) updates as the grid changes |
| staff-web | Readiness | Reserve check for a chosen date (aircraft needed, target, ready, shortfall); reserve ratio setting; latest turnaround per aircraft with a task checklist (refuel, cleaning, catering, inspection) and a ready indicator; skip a task; Start Turnaround action |

Adding a cabin fills its rows with normal seats; staff then mark special rows and blocked seats. Once saved, the layout cannot be changed.

-- All timestamps use TIMESTAMPTZ (stored as UTC). Dates such as
-- status periods are DATEs interpreted on the simulated calendar
-- from Feature 1, not the real clock.
-- end_date and planned_end_date are the LAST unavailable day (inclusive).
-- Table names are singular. Layout validation, format checks, task and maintenance
-- state consistency and the readiness calculation are the backend's job.

-- Needed for the no-overlap constraint on status periods.
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- staff table is owned by Feature 7 / core (see Feature 7 doc).

CREATE TABLE aircraft_type (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  code TEXT NOT NULL,                       -- e.g. 'A320', or 'A320-V2' for a new layout
  manufacturer TEXT NOT NULL,
  model TEXT NOT NULL,
  layout JSONB NOT NULL,                    -- seat map as rules; validated by the backend on create
  hold_weight_limit_kg INTEGER NOT NULL CHECK (hold_weight_limit_kg > 0),
  max_takeoff_weight_kg INTEGER NOT NULL CHECK (max_takeoff_weight_kg > 0),  -- Feature 2's per-tonne fees
  max_range_km INTEGER NOT NULL CHECK (max_range_km > 0),
  min_turnaround_minutes INTEGER NOT NULL CHECK (min_turnaround_minutes > 0),
  operating_cost_per_hour NUMERIC(12, 2) NOT NULL CHECK (operating_cost_per_hour >= 0),  -- per block hour
  cost_currency CHAR(3) NOT NULL,
  is_active BOOLEAN NOT NULL DEFAULT true,  -- retire a type without deleting it
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

CREATE UNIQUE INDEX aircraft_type_code_uq ON aircraft_type (code) WHERE deleted_at IS NULL;

-- The layout is write-once.
CREATE FUNCTION aircraft_type_forbid_layout_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.layout IS DISTINCT FROM OLD.layout THEN
    RAISE EXCEPTION 'aircraft_type.layout cannot change; create a new aircraft type';
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER aircraft_type_layout_once
  BEFORE UPDATE OF layout ON aircraft_type
  FOR EACH ROW EXECUTE FUNCTION aircraft_type_forbid_layout_change();

-- tail_number is the registration; there is no separate registration column.
CREATE TABLE aircraft (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tail_number TEXT NOT NULL,
  aircraft_type_id UUID NOT NULL REFERENCES aircraft_type (id),
  entry_into_service_date DATE NOT NULL,
  retired_on DATE,                          -- last day in the fleet; NULL = still flying
  base_airport_code TEXT NOT NULL,          -- airport master data is Feature 2's
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

CREATE UNIQUE INDEX aircraft_tail_number_uq ON aircraft (tail_number) WHERE deleted_at IS NULL;
CREATE INDEX aircraft_type_idx ON aircraft (aircraft_type_id);
CREATE INDEX aircraft_base_idx ON aircraft (base_airport_code);

-- No row for a date means in service.
-- origin = 'maintenance' periods belong to an aircraft_maintenance window and change only
-- through it; the backend never creates an 'in_maintenance' period any other way.
CREATE TABLE aircraft_status_period (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aircraft_id UUID NOT NULL REFERENCES aircraft (id),
  status TEXT NOT NULL
    CHECK (status IN ('in_service', 'grounded', 'in_maintenance')),
  origin TEXT NOT NULL DEFAULT 'manual'
    CHECK (origin IN ('manual', 'maintenance')),
  reason TEXT,
  start_date DATE NOT NULL,
  end_date DATE,                            -- inclusive last day; NULL = open-ended
  created_by UUID NOT NULL REFERENCES staff (id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ,
  CHECK (end_date IS NULL OR end_date >= start_date),
  -- Two live periods for one aircraft may not overlap. The backend first closes an
  -- open-ended period that a new one starts inside (same transaction).
  EXCLUDE USING gist (
    aircraft_id WITH =,
    daterange(start_date, end_date, '[]') WITH &&
  ) WHERE (deleted_at IS NULL)
);

CREATE INDEX aircraft_status_period_changed_idx ON aircraft_status_period (updated_at);

-- A maintenance window. Saving one inserts its in_maintenance status period in the same
-- transaction, so availability reads one source.
CREATE TABLE aircraft_maintenance (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aircraft_id UUID NOT NULL REFERENCES aircraft (id),
  maintenance_type TEXT NOT NULL
    CHECK (maintenance_type IN ('a_check', 'b_check', 'c_check', 'd_check', 'unscheduled')),
  planned_start_date DATE NOT NULL,
  planned_end_date DATE NOT NULL,           -- last day the aircraft is unavailable
  actual_end_date DATE,
  status TEXT NOT NULL DEFAULT 'planned'
    CHECK (status IN ('planned', 'in_progress', 'completed', 'cancelled')),
  status_period_id UUID NOT NULL UNIQUE REFERENCES aircraft_status_period (id),
  created_by UUID NOT NULL REFERENCES staff (id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ,
  CHECK (planned_end_date >= planned_start_date),
  -- A completed window must have its actual end: completing it shortens or extends
  -- the status period to that date.
  CHECK (status <> 'completed' OR actual_end_date IS NOT NULL)
);

CREATE INDEX aircraft_maintenance_aircraft_idx ON aircraft_maintenance (aircraft_id, planned_start_date DESC);

-- No rows = may fly every day. The set is replaced as a whole.
CREATE TABLE aircraft_operating_day (
  aircraft_id UUID NOT NULL REFERENCES aircraft (id),
  day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 1 AND 7),  -- 1 = Monday
  PRIMARY KEY (aircraft_id, day_of_week)
);

-- One per flight. Readiness is derived from the tasks (query below), not stored.
CREATE TABLE aircraft_turnaround (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  aircraft_id UUID NOT NULL REFERENCES aircraft (id),
  flight_id UUID NOT NULL,                  -- Feature 2's flight (cross-module)
  airport_code TEXT NOT NULL,               -- where it actually landed (cross-module)
  arrived_at TIMESTAMPTZ NOT NULL,          -- simulation clock
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

-- Makes POST /aircraft/:id/turnarounds safe to repeat (retries, the Start Turnaround button):
-- INSERT ... ON CONFLICT DO NOTHING, then create the four tasks in the same transaction.
CREATE UNIQUE INDEX aircraft_turnaround_flight_uq ON aircraft_turnaround (flight_id) WHERE deleted_at IS NULL;
CREATE INDEX aircraft_turnaround_latest_idx ON aircraft_turnaround (aircraft_id, arrived_at DESC) WHERE deleted_at IS NULL;

-- started_at / completed_at use the simulation clock. skipped counts as done.
CREATE TABLE aircraft_turnaround_task (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  turnaround_id UUID NOT NULL REFERENCES aircraft_turnaround (id),
  task_type TEXT NOT NULL
    CHECK (task_type IN ('refuel', 'cleaning', 'catering', 'inspection')),
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'in_progress', 'completed', 'skipped')),
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  UNIQUE (turnaround_id, task_type)
);

-- Feature 9's own setting. The value is validated by the backend.
CREATE TABLE fleet_setting (
  key TEXT PRIMARY KEY CHECK (key IN ('reserve_ratio')),
  value TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by UUID REFERENCES staff (id)
);

INSERT INTO fleet_setting (key, value) VALUES ('reserve_ratio', '1.10');
