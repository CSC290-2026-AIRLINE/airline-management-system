## Overview

Feature 7 covers the people on the Flython platform: customers who hold an account, passengers who fly, how passengers are related, and the security screening that runs at booking and check-in. It has three actors:

- **Customer** — signs in, buys tickets, views and updates their own profile, manages saved passengers (family and companions they book for) and their profile photo.
- **Staff** — searches customers and passengers and views their detail to support customer service. Detail is read-only except for correcting a passenger's date of birth, gender or nationality.
- **Security staff** — maintain the watchlist and review screening matches that hold a passenger's check-in.

Authentication (Clerk, OAuth-only) is out of scope for this feature's diagram and UI, but the session-exchange flow that provisions a customer's local account is part of the backend design below.

**Customer vs passenger.** A customer is the account holder who signs in and pays. A passenger is anyone named on a ticket and never needs an account. Passengers are kept as `passenger` rows linked to the customers who book them, so the same person can have more than one row (one per customer who books them). Screening therefore matches and remembers decisions by identity data (passport and nationality, or normalised name and date of birth), never by `passenger_id` alone.

## Data model

Six tables carry Feature 7's data; all table names are singular. `customer` links to the shared `user` table through a composite foreign key on `(user_id, user_type)`, so a user row can't be both a customer and staff. A customer's own identity is the `passenger` row in `customer.passenger_id`. `user` and `staff` live in the baseline schema, and the cross-module foreign key to feature 2's flight lives in the shared cross-module file.

| Table | Key columns | Notes |
| --- | --- | --- |
| `customer` | `user_id` (FK), `passenger_id` (FK, own identity), phone, profile photo URL | One row per account holder; email lives on `user` |
| `passenger` | first/last name (passport spelling), local first/last name, DOB, gender (`M`/`F`/`X`), nationality (2-letter code), passport number | One row per customer who books the person, so duplicates are expected. DOB, gender and nationality are set once; after that only a staff correction changes them |
| `customer_passenger` | `customer_id`, `passenger_id`, `relationship_type`, `is_saved`, `last_booked_at` | Who a customer books for. Relationship is the passenger relative to the customer (`parent` = the passenger is the customer's parent). Removing from the saved list sets `is_saved = false`; feature 3b writes `last_booked_at` |
| `watchlist_entry` | name, DOB, nationality, passport number, `list_type`, `status`, issuing authority, reason, who cleared it and why | Wanted, travel-ban and no-fly records; `status` active or cleared replaces separate "current" and "former" tables |
| `screening_check` | `run_id`, `passenger_id`, `flight_id`, `trigger_point`, `watchlist_entry_id`, `match_level`, `outcome`, snapshot of the identity compared | One row per matched entry in a run (one `none` row for a clean run). Never updated or deleted |
| `screening_review` | `screening_check_id`, `decision`, reviewer, required note, authority notified at | A security decision on a check. Append-only; the latest review for a check wins |

**Deliberately excluded from scope:** consent logs, tier/membership fields, travel document storage, data-export requests, and account-deletion requests. These were cut during scoping and the cut is agreed. Seat and meal preferences were removed as well.

## Auth & provisioning

Clerk handles authentication only — OAuth sign-in, no password flows to build or manage. Each app (customer-web, staff-web) has its own isolated Clerk app. The backend never trusts the Clerk session directly; it exchanges it for its own tokens:

1. Customer signs in via Clerk (OAuth) on customer-web.
2. Frontend sends the Clerk session token to the NestJS backend's session-exchange endpoint.
3. Backend verifies the Clerk token, then finds or creates the local `user`, `passenger` and `customer` rows for that person in one transaction (`INSERT … ON CONFLICT` on `clerk_user_id`), and copies the verified Clerk email into `user.email` at every sign-in. No Clerk webhook is needed.
4. Backend issues its own short-lived JWT access token plus a rotating, httpOnly refresh-token cookie (with reuse detection).
5. Frontend uses the JWT for all subsequent API calls; the refresh cookie silently renews the session.

Staff-web follows the same pattern with its own Clerk app and role claim.

**First sign-in setup.** OAuth sign-in doesn't provide date of birth, gender or nationality. After the first sign-in, the customer enters them once on a setup screen (`PUT /customers/me/identity`); they are locked from then on, and only staff can correct a mistake: Correct identity on the staff passenger detail (\`PUT /staff/passengers/:id/identity\`) needs a reason and a passport check, is logged in feature 15's audit log, and re-screens the passenger's upcoming flights.

**Email change.** Clerk handles it: the customer adds the new email in Clerk's account flow, Clerk sends and checks the verification code, and the new address becomes primary only once verified. At the next session exchange the backend reads the primary email from the verified Clerk session and copies it into `user.email`, so the two stay in step without a table or routes of our own.

**Migration (agreed with Feature 1).** The new `customer` table replaces the scaffold one: names, DOB, gender and nationality move to `passenger`, and seat and meal preferences are dropped. A data-moving migration copies existing rows, and `auth.service.ts` and `seed.ts` change with it.

## Passengers at booking

Only the customer signs in; passengers are typed into the booking form and kept as `passenger` rows linked to that customer, so they never need an account.

1. The customer signs in and starts a booking (feature 3a).
2. For each passenger, typing a name searches the customer's own identity plus their saved passengers: typing "ก" lists names starting with ก, in Thai or passport spelling, most recently booked first.
3. Picking a name fills the form. A new name creates a `passenger` row and a `customer_passenger` link. Thai or accented names are transliterated before the Latin (passport) fields are stored.
4. Date of birth is required for every passenger before the booking can be confirmed (feature 6 needs it for APIS, and screening needs it). Passport number can wait until check-in.
5. The customer can set how the passenger is related to them (for example, child), stored as `relationship_type` on the same `customer_passenger` row. When the booking is confirmed, feature 3b writes `last_booked_at`.

Autocomplete only searches the signed-in customer's own linked passengers, so one customer never sees another's family. Staff booking on a customer's behalf can search all passengers, and create a passenger and link it to that customer (`POST /staff/passengers`).

## Security screening & check-in

Every passenger is screened against active watchlist entries at booking, at check-in, when an entry is added, edited or reactivated, and when the passenger's name, passport or identity changes. Only check-in can block: a likely match holds check-in until security staff decide. Features 3b and 6 call `POST /screening/check`; it returns `clear`, `held` or `denied`.

&#91;image: Feature 7 security screening flow at check-in\]

| Match level | Rule |
| --- | --- |
| Strong | Passport number and nationality equal an active entry |
| Probable | Passport number equal with a different or missing nationality, or name similarity at least 0.5 with an equal DOB |
| Weak | Name similarity at least 0.6 with a different or missing DOB |
| None | No active entry reaches Weak |

Name similarity is trigram similarity on `name_key(first, last)` (uppercase letters and digits only), scored in both name orders (first+last and last+first) and taking the higher, because Thai names are often swapped between the two fields. 0.5 and 0.6 are starting values to tune; a one-letter typo scores about 0.6.

| Trigger point | Strong or probable | Weak | None | API returns |
| --- | --- | --- | --- | --- |
| `check_in` (feature 6) | `held` | `flagged` | `clear` | `held` if any entry is held, else `clear` |
| `booking` (feature 3b) | `flagged` | `flagged` | `clear` | always `clear`; never blocks the purchase |
| `new_entry`, `entry_change` (background job) | `flagged` | `flagged` | no row | n/a |
| `identity_change` (name, passport or staff correction) | `flagged` | `flagged` | `clear` | n/a |

A prior `false_positive` for the same identity, flight and entry skips that entry. A prior `confirmed` returns `denied`. If screening can't run, check-in fails closed (treated as held, passenger sees "see an agent") and booking fails open, with the skip recorded.

- The system never denies on its own: a held or flagged check with no review appears in the Screening Queue, and a security officer opens it on the Screening Review screen to confirm or release it, with a required note.
- Each `POST /screening/check` call is one run (`run_id`): one `screening_check` row per matched entry, or one `none` row for a clean run. Rows are never updated or deleted, and each keeps a snapshot of the identity it compared (name key, DOB, nationality, passport), so the review screen shows what matched, not today's values.
- A decision is a row in `screening_review`. Reviews are append-only and the latest one for a check wins, so a wrong decision can be corrected with history kept.
- Decisions are remembered by identity, not by `passenger_id`: the same passenger row, or the same passport and nationality when either side has a passport, or the same name key and DOB only when neither has one. This stops one cleared person from clearing a different person with the same name and DOB.
- Confirmed match: check-in stays denied, the authority is notified through feature 13 (mocked) and the decision is logged in feature 15's audit log.
- The passenger only sees "Please see an agent at the airport", never that they matched a watchlist.
- Clearing a watchlist entry records who cleared it, when and why. Watchlist entries are typed in by security staff as demo data; no real police or immigration database is connected.
- Formats are normalised by the backend so values compare: gender `M`, `F` or `X`; nationality a 2-letter lowercase code (`th`, `hk`, `jp`, `mm`) in both `passenger` and `watchlist_entry`, converted from the 3-letter codes in passports and feature 6's MRZ reader (`THA` → `th`); passport uppercase letters and digits only.
- Privacy: opening passenger or customer detail is audited as `view_sensitive`; passport numbers are masked for non-security staff; passport and DOB are masked in audit entries; only the security role sees the watchlist and the screening screens.
- Feature 7 owns the watchlist and the matching rules; features 3b and 6 only call `POST /screening/check` (agreed with the feature 6 team).

### Backend rules (not database constraints)

- Formats above; names not blank; DOB not before 1900 and not after the simulation date; DOB required before a booking is confirmed.
- The identity lock: DOB, gender and nationality set once, then only `PUT /staff/passengers/:id/identity`.
- Outcome consistent with match level and trigger point: one function builds the screening rows from the tables above, with a test for each row.
- A clean check is never reviewed; the review note is not blank; the authority is notified only for a confirmed match.
- No update or delete path for `screening_check` or `screening_review`.

## API routes

Guard labels: `C` = customer, `S` = staff, `Sec` = security staff, `Sys` = service-to-service call from feature 3b or 6. Writes use POST to create and PUT to update — no PATCH.

| Route | Method | Guard | Purpose |
| --- | --- | --- | --- |
| `/customers/me` | GET | C | View own profile |
| `/customers/me` | PUT | C | Update own profile (name, phone); a name change re-screens upcoming flights; email changes go through Clerk |
| `/customers/me/identity` | PUT | C | One-time setup of DOB, gender and nationality; rejected once they are set |
| `/customers/me/photo` | PUT | C | Upload profile photo |
| `/customers/me/photo` | DELETE | C | Remove profile photo |
| `/customers/me/passengers` | GET | C | Own identity plus saved passengers; `?q=` name prefix for booking autocomplete |
| `/customers/me/passengers` | POST | C | Add a passenger (DOB required), with optional relationship |
| `/customers/me/passengers/:id` | PUT | C | Edit a saved passenger and their relationship; a name or passport change re-screens |
| `/customers/me/passengers/:id` | DELETE | C | Remove from saved list (`is_saved = false`); the passenger row stays for past bookings |
| `/staff/customers` | GET | S | Search customers |
| `/staff/customers/:id` | GET | S | View customer detail; audited as `view_sensitive` |
| `/staff/passengers` | GET | S | Search all passengers by name, DOB or passport number |
| `/staff/passengers` | POST | S | Create a passenger and link it to a customer when booking on their behalf |
| `/staff/passengers/:id` | GET | S | View passenger detail and relationships; passport masked for non-security staff; audited as `view_sensitive` |
| `/staff/passengers/:id/identity` | PUT | S | Correct DOB, gender or nationality; reason required; logged in feature 15 and re-screens upcoming flights |
| `/screening/check` | POST | Sys | Screen one passenger for one flight (3b at booking, 6 at check-in); returns `clear`, `held` or `denied` |
| `/security/watchlist` | GET | Sec | List and search watchlist entries |
| `/security/watchlist` | POST | Sec | Add a watchlist entry; re-screens upcoming flights |
| `/security/watchlist/:id` | PUT | Sec | Edit, clear (who and why required) or reactivate an entry; edits and reactivation re-screen |
| `/security/screenings` | GET | Sec | Flagged or held checks with no review, nearest departure first |
| `/security/screenings/:id` | GET | Sec | Review detail: snapshot of the identity compared, booking and flight, matched entry, earlier checks and reviews |
| `/security/screenings/:id/reviews` | POST | Sec | Add a review (confirmed or false positive); note required; the latest review wins |

Error format is consistent across routes: `{ error: { code, message, details? } }`.

## SQL

```sql
-- Feature 7 (Customer and Passenger Profiles) schema.
-- "user" and staff are in 00-baseline.sql. This REPLACES the scaffold customer table in schema.sql
-- (data-moving migration agreed with Feature 1): names, DOB, gender and nationality move to passenger;
-- seat and meal preferences were cut from scope. The flight cross-module FKs are in 99-cross-module-fks.sql.
-- Formats, the identity lock, screening consistency and immutability of screening rows are backend rules.
-- All timestamps are TIMESTAMPTZ; business times come from the simulation clock.

CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- trigram similarity for fuzzy name matching

-- Normalised name used for matching: uppercase letters and digits only (Latin fields are ASCII).
-- A function, not a stored column, so there is nothing to keep in sync; indexes use the same expression.
-- Matching scores both orders, name_key(first, last) and name_key(last, first), and takes the higher.
CREATE FUNCTION name_key(first_name text, last_name text) RETURNS text
LANGUAGE sql IMMUTABLE AS $$
  SELECT upper(regexp_replace(first_name || last_name, '[^A-Za-z0-9]', '', 'g'))
$$;

-- Everyone who flies, with or without an account. Duplicates are accepted (one row per customer who books
-- the person); screening matches on identity data, never on passenger_id alone.
-- Backend normalises before insert: passport uppercase letters and digits only; nationality a 2-letter
-- lowercase code (th, hk, jp, mm) validated against a list, converted from 3-letter passport/MRZ codes.
-- DOB, gender and nationality are set once; then only a staff correction changes them.
-- DOB is required before a booking is confirmed (backend rule; a customer's own row starts empty).
CREATE TABLE passenger (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  first_name       TEXT NOT NULL,                       -- passport (Latin) spelling
  last_name        TEXT NOT NULL,
  local_first_name TEXT,                                -- e.g. Thai spelling, for autocomplete
  local_last_name  TEXT,
  date_of_birth    DATE,
  gender           TEXT CHECK (gender IN ('M', 'F', 'X')),
  nationality      TEXT,                                -- 2-letter lowercase code
  passport_number  TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at       TIMESTAMPTZ
);
CREATE INDEX passenger_passport_idx ON passenger (passport_number) WHERE passport_number IS NOT NULL;
CREATE INDEX passenger_dob_idx ON passenger (date_of_birth) WHERE date_of_birth IS NOT NULL;
CREATE INDEX passenger_first_name_prefix ON passenger (first_name text_pattern_ops);
CREATE INDEX passenger_local_first_name_prefix ON passenger (local_first_name text_pattern_ops);

-- The account holder. Their own identity is the passenger row in passenger_id (no 'self' link row).
CREATE TABLE customer (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id           UUID NOT NULL,
  user_type         TEXT NOT NULL DEFAULT 'customer' CHECK (user_type = 'customer'),
  passenger_id      UUID NOT NULL UNIQUE REFERENCES passenger (id),
  phone             TEXT,
  profile_photo_url TEXT,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at        TIMESTAMPTZ,
  FOREIGN KEY (user_id, user_type) REFERENCES "user" (id, type),
  UNIQUE (user_id)
);

-- Who a customer books for. Removing from the saved list sets is_saved = false and keeps the link.
-- relationship_type is the passenger relative to the customer ('parent' = the passenger is the customer's parent).
CREATE TABLE customer_passenger (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id       UUID NOT NULL REFERENCES customer (id),
  passenger_id      UUID NOT NULL REFERENCES passenger (id),
  relationship_type TEXT CHECK (relationship_type IN ('spouse', 'parent', 'child', 'sibling', 'guardian', 'companion', 'other')),
  is_saved          BOOLEAN NOT NULL DEFAULT true,
  last_booked_at    TIMESTAMPTZ,                         -- simulation clock; written by feature 3b
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (customer_id, passenger_id)
);
CREATE INDEX customer_passenger_recent_idx ON customer_passenger (customer_id, last_booked_at DESC NULLS LAST) WHERE is_saved;
CREATE INDEX customer_passenger_passenger_idx ON customer_passenger (passenger_id);

-- Watchlist --------------------------------------------------------------------------------------

CREATE TABLE watchlist_entry (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  first_name          TEXT NOT NULL,
  last_name           TEXT NOT NULL,
  date_of_birth       DATE,
  nationality         TEXT,                              -- normalised like passenger
  passport_number     TEXT,
  list_type           TEXT NOT NULL CHECK (list_type IN ('wanted', 'travel_ban', 'no_fly')),
  status              TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'cleared')),
  issuing_authority   TEXT NOT NULL,
  reason              TEXT,
  listed_at           TIMESTAMPTZ NOT NULL,              -- simulation clock
  cleared_at          TIMESTAMPTZ,                       -- simulation clock
  cleared_by_staff_id UUID REFERENCES staff (id),        -- backend requires who, when and why together
  clear_reason        TEXT,
  created_by_staff_id UUID NOT NULL REFERENCES staff (id),
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK ((status = 'cleared') = (cleared_at IS NOT NULL))
);
CREATE INDEX watchlist_entry_passport_idx ON watchlist_entry (passport_number) WHERE status = 'active' AND passport_number IS NOT NULL;
CREATE INDEX watchlist_entry_name_dob_idx ON watchlist_entry (name_key(first_name, last_name), date_of_birth) WHERE status = 'active';
CREATE INDEX watchlist_entry_name_trgm ON watchlist_entry USING gin (name_key(first_name, last_name) gin_trgm_ops) WHERE status = 'active';

-- Screening --------------------------------------------------------------------------------------

-- One row per (run, matched entry); a clean run is one row with match_level 'none'. Never updated or
-- deleted. Each row snapshots the identity it compared, because names and passports are editable.
-- Departure time is not copied: the queue joins feature 2's flight table (cross-module FK) so delays show.
CREATE TABLE screening_check (
  id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id             UUID NOT NULL,                      -- one POST /screening/check call or job pass
  passenger_id       UUID NOT NULL REFERENCES passenger (id),
  flight_id          UUID NOT NULL,                      -- feature 2's flight (cross-module FK)
  pnr_id             UUID,                               -- feature 3b booking, for the review screen
  trigger_point      TEXT NOT NULL CHECK (trigger_point IN ('booking', 'check_in', 'new_entry', 'entry_change', 'identity_change')),
  watchlist_entry_id UUID REFERENCES watchlist_entry (id),
  match_level        TEXT NOT NULL CHECK (match_level IN ('none', 'weak', 'probable', 'strong')),
  name_similarity    REAL,                               -- best of both name orders
  outcome            TEXT NOT NULL CHECK (outcome IN ('clear', 'flagged', 'held')),
  snap_name_key      TEXT NOT NULL,                      -- identity as compared
  snap_date_of_birth DATE,
  snap_nationality   TEXT,
  snap_passport      TEXT,
  occurred_at        TIMESTAMPTZ NOT NULL,               -- simulation clock
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Idempotency: retries and job re-runs cannot duplicate a hit. entry_change and identity_change are
-- excluded because an entry can be edited, and a passenger corrected, more than once.
CREATE UNIQUE INDEX screening_check_once_uq
  ON screening_check (passenger_id, flight_id, watchlist_entry_id, trigger_point)
  WHERE watchlist_entry_id IS NOT NULL AND trigger_point IN ('booking', 'check_in', 'new_entry');
CREATE INDEX screening_check_flight_idx ON screening_check (flight_id);
CREATE INDEX screening_check_passenger_idx ON screening_check (passenger_id, occurred_at DESC);
CREATE INDEX screening_check_open_idx ON screening_check (flight_id) WHERE outcome IN ('flagged', 'held');

-- Decisions. Append-only: a wrong decision is corrected by a newer review, and the latest one wins.
-- Screening Queue = flagged or held checks with no review, joined to feature 2's flight, nearest departure first.
CREATE TABLE screening_review (
  id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  screening_check_id    UUID NOT NULL REFERENCES screening_check (id),
  decision              TEXT NOT NULL CHECK (decision IN ('confirmed', 'false_positive')),
  reviewed_by_staff_id  UUID NOT NULL REFERENCES staff (id),
  review_note           TEXT NOT NULL,
  reviewed_at           TIMESTAMPTZ NOT NULL,            -- simulation clock
  authority_notified_at TIMESTAMPTZ,                     -- simulation clock; feature 13 is mocked
  created_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX screening_review_latest_idx ON screening_review (screening_check_id, reviewed_at DESC);

-- Soft delete: passenger and customer rows set deleted_at, never DELETE; queries filter deleted_at IS NULL.
-- customer_passenger uses is_saved, watchlist_entry uses status, and screening rows are permanent records.
```
