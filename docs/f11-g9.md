## Overview

Feature 11 is the Flython loyalty programme: customers join, earn miles on flights they fly, qualify for tiers, and spend miles on award seats. It has two actors plus four background jobs:

- **Customer (member)** — joins the programme and gets a member number, sees the miles balance and a statement, sees how far the next tier is and when the current tier expires, and pays for a booking with miles at checkout when award seats are released (taxes and surcharges still go on the card), and uses tier benefits: lounge access, extra baggage, priority check-in and boarding, a complimentary upgrade and travel insurance.
- **Staff (loyalty admin)** — defines tier rules and earning rates, releases award seats per flight and cabin, looks up members, adjusts a balance by hand with a reason, sets tier benefits, and admits members at the lounge desk.
- **Background jobs** — run on the simulation clock, never the real clock: earn miles when a flight is completed, re-evaluate tiers, expire old miles, and upgrade eligible members into free higher-cabin seats before departure.

Authentication (Clerk, OAuth-only) is out of scope here; a member is a Feature 7 customer row that has joined.

**Who earns miles.** Miles go to the member who booked, not the person who sat in the seat. A boarded passenger credits the member who owns the booking (`booking.customer_id` in Feature 3b), so a member who books for family or companions earns all their miles, and the companions need no account. When staff book on behalf of a customer, that customer earns, not the agent. A booking whose customer has not joined the programme earns nothing, and only flights that arrive at or after `joined_at` earn, so a late join is never back-filled. A lap infant takes no seat and earns nothing, and neither does an award seat paid with miles. Tier qualification is stricter: it counts only the segments the member flew personally (see Tiers).

**Tier ownership.** Feature 11 owns the tier. The Feature 7 doc cut tier and membership fields from its scope, so there is nothing to write back to. The tier lives on `loyalty_member`, and features 6 and 12 read it, with the tier's benefits, through one in-process method, `tierForPassenger(passengerId)`. A missing member, no tier or an expired tier means "no tier", so a late loyalty module never blocks check-in or onboard products.

**Core demo scope.** Join, earn, statement, tier evaluation, award redemption, expiry with reminder, staff rules, award release, manual adjustment, tier benefits (lounge, baggage, priority, upgrade, insurance) and taxes on miles bookings. Pooled family accounts are stretch.

## Data model

Nine tables carry Feature 11's data; all table names are singular. `loyalty_member` links to Feature 7's `customer` (one member per customer). The miles balance sits on `loyalty_member.miles_balance`, but only a database trigger on the ledger writes it, so it always equals the sum of the member's `loyalty_transaction.miles` and every balance can be explained from history. Award seats are not stored here: Feature 3b's `seat_inventory` is the only seat count. Earn and redeem rows point at Feature 3b's `booking_coupon` (one passenger on one segment of one booking).

## Earning, tiers, redemption and expiry

### Earning

Miles per flown segment are route distance times the fare-class multiplier, rounded to whole miles:

```text
miles = round(route.distance_km × multiplier)
```

Example: a 1,000 km segment earns 1,000 miles on a full fare (1.00), 500 on a discounted fare (0.50) and 1,500 in business (1.50). Starting multipliers are values to tune in Feature 15, not fixed truth.

1. The earn job runs on the simulation clock. It takes the flights whose `arr_at` has passed, that are not cancelled, and that arrived at or after the member's `joined_at`. Feature 6's `check_in` says who was marked boarded. Once Feature 2 publishes `flight.arrived`, that event only runs the job sooner.
2. For each boarded passenger it finds the booking coupon (that passenger on that flight) and the member who owns the booking (`booking.customer_id` in Feature 3b). No member means no earn row. A lap infant and an award coupon earn nothing.
3. It reads `route.distance_km` (the planned route, already a column in Feature 2) and the coupon's fare class from the booking segment, takes the multiplier from the earn rule, and writes one earn row. A result of 0 miles writes no row.
4. The earn row carries `expires_at` (flight date plus `miles_retention_months`) and the copied distance, fare class and multiplier. A unique index allows one earn per coupon, so the job can run twice, and a missed run is caught up by the next one. No receipt table is needed.

### Tiers

The tier job re-evaluates a member after every earn and once per simulated day. The member qualifies for the highest tier whose `min_miles` or `min_flights` is met by earn rows from flights in the last 12 months, counting only coupons the member flew personally (the coupon's passenger is the member's own `customer.passenger_id`). Miles earned on companions' seats count toward the balance but not toward the tier. Redeemed, expired and adjusted miles do not change qualification. Qualifying for a tier at least as high as the current one sets `tier_qualified_at` to now and `tier_expires_at` to now plus `valid_months`; a lower result never cuts the current tier short. At `tier_expires_at` the member falls to whatever they qualify for then, or to no tier, and every reader treats an expired tier as no tier even before the job runs. The member sees the tier, the miles or flights still needed for the next one, and the expiry date.

### Redemption

An award seat uses Feature 3b's booking path, with miles instead of payment. Feature 3b owns hold, confirm, expiry and cancel; Feature 11 owns the miles.

1. The member searches for flights in Feature 3a. For each flight and cabin with released award seats, 3a asks Feature 11 for the miles cost and seats left in one batch call (seats left come from the award seats in `seat_inventory`, not from a second count), and shows "or 8,000 miles" beside the cash price, with the taxes and surcharges still due in cash (for example "or 8,000 miles + THB 1,250 taxes"). This is information only: nothing is held or spent in search, and the member picks the flight as usual.
2. On Feature 3b's Passengers & Extras page, next to the promo code, the member chooses how to pay, Card or Miles, before anything is held. Miles is offered only when every flight in the booking has enough award seats for all passengers who need a seat. The cost is `miles_cost` times the number of passengers, shown with the balance after, or the shortfall if the balance is too low. The taxes and fuel surcharges are shown as a separate amount due by card. Review & Pay then shows the miles total and the taxes due, with no Card or Miles choice.
3. Choosing miles sends `POST /bookings` with `payment_type = miles`. Feature 3b holds the award seats with its normal TTL (taking `held_count` and `award_held_count` in `seat_inventory`) and calls Feature 11's redeem method, which checks the balance and writes one redeem row (negative miles) per award coupon in the same transaction, or answers 409 if seats or miles fall short. The ledger trigger takes the member's row lock, so two bookings by one member queue and the second sees the first one's balance. There is no separate redemption table: the redeem row is the redemption.
4. The fare is paid in miles, but taxes and fuel surcharges are not. Feature 4 prices them for the award seat, and Feature 3b puts their total on the booking. The member pays that amount by card through Feature 5a while the hold runs, and 3b confirms the booking when 5a confirms the payment. If the card payment fails or the hold lapses, 3b releases the booking and the miles return. A booking with no taxes due skips 5a and confirms at once.
5. Whenever Feature 3b expires or cancels an award coupon (a lapsed hold, a cancellation by the customer or staff, or a flight cancelled with refund or partner rebook), it calls Feature 11's reverse method in the same transaction. A `redeem_reversal` row names the redeem row it gives back, at most once and only for the same member. Feature 5b refunds the taxes already paid.

### Return to cash

Award seats are for members who plan ahead, so redemption closes `award_cutoff_hours` (starting 72) before departure. A job on the simulation clock runs every hour, and for each flight inside that window it reads how many award seats are held or sold in each cabin from `seat_inventory` and calls Feature 3b's `setAwardSeats(flightId, cabin, n)` with that number. 3b lowers `award_limit` to it, so the unredeemed seats become ordinary cash seats at once, with no move between fare classes. A hold that lapses after the cutoff lowers `award_limit` in the same step. Running the job twice changes nothing.

### Expiry

Miles expire after `miles_retention_months` (starting value 36). The expiry job treats redeem rows without a reversal, and negative adjustments, as debits. Earn rows and positive adjustments, each less any expire row that points at it, are credits. Debits use up the credits with the earliest `expires_at` first. A credit past its `expires_at` with miles left gets one expire row for exactly that amount. `expiry_reminder_days` (starting value 30) before, it sends one `miles_expiring` message per member and expiry date, with the total, through Feature 13's `inbound_event` (source `11`, key `miles_expiring:<member id>:<date>`). The unique key makes a repeat a no-op, so Feature 11 records nothing.

### Manual adjustment

Staff can add or remove miles with a reason. The backend writes an adjust row and logs it in Feature 15's audit log; the row stores the audit entry id.

## Tier benefits

Feature 11 decides what each tier gets, and the other features apply it. The values are rows in `loyalty_tier_benefit`, editable through Feature 15, so the numbers below are starting values to tune.

| Benefit | No tier | Silver | Gold | Platinum |
|---|---|---|---|---|
| Lounge access | No | Member only | Member and 1 guest | Member and 2 guests |
| Extra free baggage | 0 kg | +5 kg | +10 kg | +20 kg |
| Priority check-in lane | No | No | Yes | Yes |
| Priority boarding | No | No | Yes | Yes |
| Complimentary upgrade | No | Yes, after Gold | Yes, after Platinum | Yes, first |
| Travel insurance | Not offered | Add at member price | Included | Included |

**Who gets them.** A benefit belongs to the person who flies. `tierForPassenger(passengerId)` follows passenger, then `customer.passenger_id`, then member, so a booker who is not on the flight gets nothing, and a Gold member's companions get no benefits on a trip the member does not take. Benefits apply only while the tier is valid on the simulation clock. An unknown passenger, no membership or an expired tier means no benefits, and a failed lookup never blocks the caller.

**Lounge.** Staff at the lounge desk enter a member number or booking reference and the number of guests. Feature 11 checks that the tier allows lounge access, that guests do not exceed `lounge_guests`, and that the member has a confirmed or checked-in ticket on a flight departing within the next 4 hours (read from Feature 3b). It writes a `loyalty_benefit_use` row of type `lounge_visit`. A member with no ticket for that window is refused.

**Extra baggage.** Feature 6 adds `extra_baggage_kg` to the free allowance of its `checked_bag` rule for the member. Feature 11 stores no baggage data, and Feature 10 (lost and found) does not use it.

**Priority check-in and boarding.** Feature 6 reads the two flags, sends the member to the priority lane at check-in and puts the boarding pass in the first boarding group.

**Complimentary upgrade.** An hourly job on the simulation clock handles flights departing in the next 24 hours. For each flight and each step up (economy to business, business to first), it takes the member's coupons in the lower cabin that are confirmed, not checked in and paid in cash (a booking paid with miles is not upgraded), sorted by tier rank (highest first) and then by the booking's `confirmed_at` (oldest first). It upgrades one cabin each while Feature 3b still has unsold seats in the higher cabin. For each one it calls Feature 3b's `upgradeCoupon(couponId, toCabin)`, which in one locked transaction moves a seat from the old cabin to the new one and clears the seat code (the member picks a new seat at check-in). Then it writes a `loyalty_benefit_use` row of type `upgrade` and publishes `loyalty.upgraded` for Feature 13. A coupon is upgraded at most once, no fare difference is charged or refunded, and running the job twice changes nothing.

**Travel insurance.** Gold and Platinum get a basic policy on every booking they make. Silver can add the same policy on Review & Pay at the member price, paid by card with the booking through Feature 5a. When the booking is confirmed, Feature 3b calls Feature 11's `issueInsurancePolicy(bookingId)`, which writes a `loyalty_insurance_policy` row with a policy number that covers every passenger on the booking. Cancelling the booking calls `cancelInsurancePolicy(bookingId)`, and Feature 5b refunds a price that was paid. No real insurer is called.

### Agreement needed with other teams

Features 6 and 12 read the tier from Feature 11, not from Feature 7:

- `tierForPassenger(passengerId)` is an in-process service method, not an HTTP route, so no token can reach it. It returns `{ tier_code, expires_at, benefits }`, where `benefits` is `{ lounge_guests, extra_baggage_kg, priority_checkin, priority_boarding, upgrade_eligible, insurance_price }`, or `{ tier_code: null }` for an unknown passenger, no membership or an expired tier.
- Features 6 and 12 pass the passenger who flies (Feature 12 the passenger of the order line). Feature 7 marks the member's own passenger row with `customer.passenger_id`.
- Callers treat an error, a timeout or a null as "no tier" and carry on.
- The rev6 spec says the tier is written onto Feature 7's profile. The Feature 7 doc cut that field, so this replaces it. Lock this contract by week 3 to 4, as for all cross-module APIs.

### Agreement needed with Feature 2

Feature 11 reads `route.distance_km`, `flight.arr_at` and `flight.status` directly, so no new column and no event is needed. To lock by week 3 to 4:

- Feature 2 keeps `route.distance_km`, `route_id`, `flight.arr_at` and `flight.status` stable and tells us before renaming them.
- Feature 2 has no job yet that writes departed or arrived, so the earn job does not wait for it: it uses `arr_at` on the simulation clock. The `flight.arrived` event, once it exists, only runs the job sooner.
- Whether a diverted flight gets `flight.arrived`. Feature 11 skips earning whenever `actual_destination` is set (see Open questions).

### Backend rules (not database constraints)

- The simulation clock is the only time source for `occurred_at`, `expires_at`, hold times, tier windows and every job. No code calls the real system clock.
- A customer can join once; joining creates the `loyalty_member` row and a member number in one transaction.
- The ledger is append-only: a trigger refuses update, delete and truncate of `loyalty_transaction`. `loyalty_member.miles_balance` is written only by a trigger on each ledger insert, which takes the member's row lock and also writes `balance_after` and `seq` on the new row. A `CHECK (miles_balance >= 0)` refuses a spend below zero, so two spends by one member queue and the second is refused if the balance is short.
- One earn and one redeem per `booking_coupon` (unique index), so the earn job can run twice, and two members can never share one seat's miles.
- An earn row exists only for a coupon marked boarded in Feature 6, on a flight whose `arr_at` has passed on the simulation clock, that is not cancelled and arrived at or after the member's `joined_at`. No-shows earn nothing, and neither does a lap infant, an award coupon (it has no fare class) or a result of 0 miles.
- Miles are whole numbers; `distance_km`, `fare_class_id` and `multiplier` are copied onto the earn row, and `miles = round(distance_km * multiplier)` is checked, so a later rule change never rewrites history.
- A redemption needs award seats left in Feature 3b's `seat_inventory` (`award_limit` minus `award_held_count` and `award_sold_count`) for every flight, and enough miles for every award coupon, checked in the same transaction that writes the redeem rows. The last seat, cash or miles, is settled by the cabin's one row lock in 3b. If any flight lacks seats or the balance is short, nothing is written and 3b answers 409.
- Feature 3b owns hold, confirm, expiry and cancel of award coupons and calls Feature 11's reverse method in the same transaction when they expire or are cancelled. A `redeem_reversal` row names the redeem row it gives back (`reversed_transaction_id`), at most once and only for the same member.
- Inside `award_cutoff_hours` of departure the release cannot be raised and no new redemption is accepted; the return-to-cash job lowers `award_limit` to the award seats in use through `setAwardSeats` and is safe to repeat.
- An expire row points at one credit (an earn row or a positive adjustment) of the same member, at most once, and is never larger than what remains of it. `expires_at` is set exactly on earn rows and positive adjustments.
- The tier job counts only earn rows in the rolling 12 months from coupons the member flew personally. Qualifying for a tier at least as high as the current one resets `tier_qualified_at` and `tier_expires_at`; a lower result never cuts the current tier short; at `tier_expires_at` the member falls to what they qualify for then. The job sends `tier_changed` on a change. Readers treat an expired tier as no tier.
- Manual adjustment needs a non-blank reason and an audit entry in Feature 15 first; the adjust row stores that entry id and the staff id, and only adjust rows carry them. Only staff with the loyalty role can adjust.
- Rule values (`multiplier`, `min_miles`, `min_flights`) and the `loyalty_setting` values (retention months, reminder days, award cutoff hours) are read at job time, not hard-coded.
- `tierForPassenger` never fails a caller: an unknown passenger, no membership or an expired tier returns `{ tier_code: null }`.
- Other features call Feature 11 through in-process service methods, not `/internal` routes. Job runs are a staff route for demos and tests, never open to customers.
- Feature 11 subscribes to no Feature 2 event. The earn job sweeps arrived flights on the simulation clock, and once `flight.arrived` exists it only runs the job sooner, so a missed event costs nothing and nothing here blocks Feature 2.
- A cancelled flight earns nothing. When Feature 2 cancels a flight, Feature 3b cancels its coupons and calls the reverse method for award coupons, so the miles come back whether the resolution is a refund or a partner rebook. Feature 11 keeps no redemption status and no `held_until` job.
- Miles use the planned `route.distance_km`, not the delay or holding time. A flight with `actual_destination` set (diverted) earns nothing automatically; staff add the miles by hand with an adjustment and a reason.
- Award seats can be released only for a flight that has not departed and is not cancelled (status `scheduled` or `delayed`), judged on the simulation clock. Releasing writes the miles price and raises `award_limit` through `setAwardSeats` in one transaction.
- A miles booking owes the taxes and fuel surcharges from Feature 4 in cash. The booking total (the sum of its coupons' prices) is that amount, and 3b confirms only after 5a captures it. Miles are never accepted in place of taxes. If no taxes are due the booking confirms at once. The miles are spent at hold and come back if the booking expires or is cancelled.
- A lap infant takes no award seat, has no redeem row and earns nothing, the same interim rule as Feature 3 until Feature 4 prices infants.
- Benefits are read from `loyalty_tier_benefit` when they are used, apply only to the passenger who flies, and only while `tier_expires_at` is in the future on the simulation clock.
- A lounge visit needs a tier that allows the lounge, guests no higher than `lounge_guests`, and a confirmed or checked-in ticket on a flight departing within 4 hours. A member has at most one lounge visit per flight (unique index).
- An upgrade moves a coupon up one cabin only, once per coupon (unique index), only for cash-paid bookings, only into seats still unsold, and in tier-rank order. It never takes a seat from another passenger and is never undone.
- A booking has at most one active insurance policy. The price is taken from the tier when the booking is confirmed; a paid price is refunded through 5b if the booking is cancelled.

## API routes

Guard labels: **Pub** = anyone, **C** = customer, **S** = staff with the loyalty-admin role, behind the shared staff-only guard from the auth owner. Other features do not call Feature 11 over HTTP: they call the service methods listed after this table, so no customer token can reach them. Writes use POST to create and PUT to update, with no PATCH. Rows are never deleted.

| Route | Method | Guard | Purpose |
|---|---|---|---|
| `/loyalty/members` | POST | C | Join the programme; returns the member number |
| `/loyalty/members/me` | GET | C | Member number, miles balance, tier, tier expiry, and miles or flights to the next tier |

## Open questions

- **Who counts toward the tier (decide).** The booker keeps all the miles, but tier qualification counts only coupons the member flew personally, so booking 20 seats on one flight does not reach Silver. This is the review's suggestion; confirm or choose another rule.
- **Diverted flights.** Today a diverted flight earns nothing automatically and staff adjust by hand, but an adjustment does not count toward the tier. Suggestion: credit it on the planned distance like any other flight.
- **Feature 3 doc.** It still has Card or Miles on Review & Pay and a confirm call for a redemption. It needs the same change as here: choose before the hold on Passengers & Extras, and no redemption to confirm, because the redeem row is the redemption.
- **Feature 7.** Please add `customer.passenger_id`, the member's own passenger row, which the tier lookup and tier qualification both need.
- **Feature 6.** Confirm it reads `extra_baggage_kg` from `loyalty_tier_benefit` instead of a new `bonus_baggage_kg` column on the tier rule (the review proposed the column; the benefits table already holds the value).
- **Feature 4.** What a lap infant pays. Until then an infant takes no award seat and earns nothing.
- **Money type.** `insurance_price` and the policy price are whole minor units, while Feature 3 and Feature 4 use `NUMERIC(12, 2)`. Pick one before 5a charges the Silver add-on.
- **Staff guard.** The shared staff-only guard from the auth owner, and the loyalty-admin role seeded in `seed.ts`.

## SQL

```sql
-- Feature 11 (Loyalty Programme) schema. All table names are singular.
-- Applies on top of the repo's migrations, the Feature 6, 10 and 13 migrations and feature-3.sql: earn and redeem rows
-- point at feature 3's booking_coupon, award seats are counted in feature 3's seat_inventory, and the two new message
-- types go into feature 13's notification_type. Uses staff (feature 1), customer (feature 7), fare_class (feature 4),
-- audit_log (feature 15) and forbid_mutation(). The foreign keys to other features are in the cross-module section.
-- Backend rules (not constraints): tier evaluation, the expiry allocation, the return-to-cash job, sales windows and who
-- may earn (see Backend rules).
-- Business timestamps (joined_at, tier_qualified_at, tier_expires_at, occurred_at, expires_at, used_at, issued_at,
-- cancelled_at) have no default and come from the simulation clock. created_at and updated_at are real time, and the
-- backend sets updated_at on every update.
-- Rows are never deleted: members and the ledger are permanent, and a mistake in the ledger is fixed by a new row.

-- Settings ---------------------------------------------------------------------------------------------------

-- Closed list of keys, like crew_setting and check_in_setting. Values are validated by the backend and read at job time.
-- award_cutoff_hours is also read by feature 3b, which stops miles bookings at the same moment.
CREATE TABLE loyalty_setting (
  key        TEXT PRIMARY KEY CHECK (key IN ('miles_retention_months', 'expiry_reminder_days', 'award_cutoff_hours')),
  value      TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by UUID REFERENCES staff (id)
);

INSERT INTO loyalty_setting (key, value) VALUES
  ('miles_retention_months', '36'),
  ('expiry_reminder_days', '30'),
  ('award_cutoff_hours', '72');

-- Rules ------------------------------------------------------------------------------------------------------

-- One row per tier, keyed by the code that features 6 and 12 name. The rows come with the migration; staff edit the
-- numbers only. A member qualifies on miles OR flights in the rolling 12 months, so a threshold of 0 would give the tier
-- to everyone. The baggage bonus lives in loyalty_tier_benefit.extra_baggage_kg, which feature 6 adds to its allowance.
CREATE TABLE loyalty_tier_rule (
  code                TEXT PRIMARY KEY,
  name                TEXT NOT NULL,
  rank                SMALLINT NOT NULL UNIQUE CHECK (rank > 0),  -- higher = better tier
  min_miles           INTEGER NOT NULL CHECK (min_miles > 0),
  min_flights         INTEGER NOT NULL CHECK (min_flights > 0),
  valid_months        SMALLINT NOT NULL DEFAULT 12 CHECK (valid_months > 0),
  updated_by_staff_id UUID REFERENCES staff (id),
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Thresholds are the starting values, for tuning through feature 15.
INSERT INTO loyalty_tier_rule (code, name, rank, min_miles, min_flights, valid_months) VALUES
  ('silver', 'Silver', 1, 15000, 20, 12),
  ('gold', 'Gold', 2, 40000, 50, 12),
  ('platinum', 'Platinum', 3, 80000, 100, 12);

-- Miles multiplier per feature 4 fare class: miles = round(distance_km * multiplier). A class with no row, or with
-- multiplier 0, earns nothing. Award seats have no fare class, so they never earn.
CREATE TABLE loyalty_earn_rule (
  fare_class_id       UUID PRIMARY KEY,                     -- feature 4's fare_class (cross-module FK)
  multiplier          NUMERIC(4, 2) NOT NULL CHECK (multiplier >= 0),
  updated_by_staff_id UUID REFERENCES staff (id),
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Members -----------------------------------------------------------------------------------------------------

CREATE SEQUENCE loyalty_member_number_seq START 10000001 MAXVALUE 99999999;

-- One member per customer. miles_balance is written only by the ledger trigger below, so it always equals the sum of
-- the member's ledger rows; the CHECK makes a spend that would go below 0 fail. The tier columns are all set or all NULL
-- (NULL = no tier); an expired tier counts as no tier even before the tier job clears it.
CREATE TABLE loyalty_member (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id       UUID NOT NULL UNIQUE REFERENCES customer (id),
  member_number     TEXT NOT NULL UNIQUE DEFAULT ('FL' || nextval('loyalty_member_number_seq')),
  miles_balance     INTEGER NOT NULL DEFAULT 0 CHECK (miles_balance >= 0),
  tier_code         TEXT REFERENCES loyalty_tier_rule (code),
  tier_qualified_at TIMESTAMPTZ,
  tier_expires_at   TIMESTAMPTZ,
  joined_at         TIMESTAMPTZ NOT NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (num_nonnulls(tier_code, tier_qualified_at, tier_expires_at) IN (0, 3)),
  CHECK (tier_expires_at > tier_qualified_at)
);

CREATE INDEX loyalty_member_tier_expiry_idx ON loyalty_member (tier_expires_at) WHERE tier_code IS NOT NULL;

-- Code may change the tier columns but never miles_balance, which only the ledger trigger (one level down) writes.
CREATE FUNCTION loyalty_member_balance_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF pg_trigger_depth() < 2 AND (TG_OP = 'INSERT' AND NEW.miles_balance <> 0
      OR TG_OP = 'UPDATE' AND NEW.miles_balance IS DISTINCT FROM OLD.miles_balance) THEN
    RAISE EXCEPTION 'miles_balance changes only through loyalty_transaction'
      USING ERRCODE = 'check_violation', CONSTRAINT = 'loyalty_member_balance_guard';
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER loyalty_member_balance_guard
  BEFORE INSERT OR UPDATE ON loyalty_member
  FOR EACH ROW EXECUTE FUNCTION loyalty_member_balance_guard();

-- Award seats ------------------------------------------------------------------------------------------------

-- The miles price of award seats on one flight and cabin. The seats themselves are feature 3's: seat_inventory's
-- award_limit is how many are set aside for miles, and award_held_count and award_sold_count how many are taken, so the
-- last seat, cash or miles, is settled by that one row lock. Releasing seats writes this row and raises award_limit in
-- one transaction; returning them to cash lowers award_limit only.
CREATE TABLE loyalty_award_release (
  flight_id            UUID NOT NULL,
  cabin                TEXT NOT NULL,
  miles_cost           INTEGER NOT NULL CHECK (miles_cost > 0),   -- per seat
  released_by_staff_id UUID NOT NULL REFERENCES staff (id),
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (flight_id, cabin)                               -- feature 3's seat_inventory (cross-module FK)
);

-- Ledger -----------------------------------------------------------------------------------------------------

-- Append-only miles ledger. Sign follows type:
--   earn             + one per boarded, paying passenger on a flight (booking_coupon_id), credited to the member who
--                      booked. distance_km, fare_class_id and multiplier are copied, so a rule change never rewrites it.
--   redeem           - one per award coupon (booking_coupon_id), the award release's miles_cost when it was held.
--   redeem_reversal  + gives back one redeem row (reversed_transaction_id) when feature 3b expires or cancels the coupon.
--   expire           - takes what is left of one earn or positive adjust row (expired_transaction_id) past expires_at.
--   adjust           +/- staff, with a reason and a feature 15 audit entry.
-- expires_at is set on every credit that can expire (earn and positive adjust). The trigger below keeps the member's
-- miles_balance, writes balance_after (the Statement's "balance after" column) and numbers the member's rows in that
-- order (seq). A row is expired or reversed at most once, and only by a row of the same member.
CREATE TABLE loyalty_transaction (
  id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  seq                     BIGINT GENERATED ALWAYS AS IDENTITY UNIQUE,
  member_id               UUID NOT NULL REFERENCES loyalty_member (id),
  type                    TEXT NOT NULL CHECK (type IN ('earn', 'redeem', 'redeem_reversal', 'expire', 'adjust')),
  miles                   INTEGER NOT NULL CHECK (miles <> 0),
  balance_after           INTEGER NOT NULL DEFAULT 0,        -- set by the trigger
  booking_coupon_id       UUID,                              -- feature 3b's coupon (cross-module FK)
  distance_km             INTEGER CHECK (distance_km > 0),
  fare_class_id           UUID,                              -- feature 4's fare_class (cross-module FK)
  multiplier              NUMERIC(4, 2),
  expires_at              TIMESTAMPTZ,
  expired_transaction_id  UUID,
  reversed_transaction_id UUID,
  reason                  TEXT CHECK (btrim(reason) <> ''),
  audit_log_id            UUID,                              -- feature 15's audit_log (cross-module FK)
  created_by_staff_id     UUID REFERENCES staff (id),
  occurred_at             TIMESTAMPTZ NOT NULL,
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, member_id),
  -- The foreign keys below make member_id that row's member, so these pairs mean "once per row". Prisma needs the pair.
  UNIQUE (expired_transaction_id, member_id),
  UNIQUE (reversed_transaction_id, member_id),
  FOREIGN KEY (expired_transaction_id, member_id) REFERENCES loyalty_transaction (id, member_id),
  FOREIGN KEY (reversed_transaction_id, member_id) REFERENCES loyalty_transaction (id, member_id),
  CHECK ((type IN ('earn', 'redeem_reversal') AND miles > 0) OR (type IN ('redeem', 'expire') AND miles < 0) OR type = 'adjust'),
  CHECK ((type IN ('earn', 'redeem')) = (booking_coupon_id IS NOT NULL)),
  CHECK (num_nonnulls(distance_km, fare_class_id, multiplier) = CASE WHEN type = 'earn' THEN 3 ELSE 0 END),
  CHECK (type <> 'earn' OR miles = round(distance_km * multiplier)),
  CHECK ((expires_at IS NOT NULL) = (type = 'earn' OR (type = 'adjust' AND miles > 0))),
  CHECK ((type = 'expire') = (expired_transaction_id IS NOT NULL)),
  CHECK ((type = 'redeem_reversal') = (reversed_transaction_id IS NOT NULL)),
  CHECK (num_nonnulls(reason, audit_log_id, created_by_staff_id) = CASE WHEN type = 'adjust' THEN 3 ELSE 0 END)
);

-- One earn and one redeem per coupon, so the earn job and a repeated redeem call can run twice.
CREATE UNIQUE INDEX loyalty_transaction_coupon_uq ON loyalty_transaction (booking_coupon_id, type) WHERE booking_coupon_id IS NOT NULL;
CREATE INDEX loyalty_transaction_member_idx ON loyalty_transaction (member_id, seq DESC);
CREATE INDEX loyalty_transaction_expiry_idx ON loyalty_transaction (expires_at) WHERE expires_at IS NOT NULL;

-- Applies each row to its member's balance. The UPDATE takes the member's row lock, so two spends by one member queue
-- and the second sees the first one's balance; a spend below 0 fails on loyalty_member's CHECK. seq is taken after the
-- lock, so one member's rows are numbered in the order their balances were applied.
CREATE FUNCTION loyalty_transaction_apply() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE loyalty_member SET miles_balance = miles_balance + NEW.miles
   WHERE id = NEW.member_id
  RETURNING miles_balance INTO NEW.balance_after;
  NEW.seq := nextval(pg_get_serial_sequence('loyalty_transaction', 'seq'));
  RETURN NEW;
END $$;

CREATE TRIGGER loyalty_transaction_apply
  BEFORE INSERT ON loyalty_transaction
  FOR EACH ROW EXECUTE FUNCTION loyalty_transaction_apply();

CREATE TRIGGER loyalty_transaction_append_only
  BEFORE UPDATE OR DELETE ON loyalty_transaction
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

CREATE TRIGGER loyalty_transaction_no_truncate
  BEFORE TRUNCATE ON loyalty_transaction
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();

-- Tier benefits ----------------------------------------------------------------------------------------------

-- What each tier gets. One row per tier, editable through feature 15. lounge_guests is NULL when the tier has no

CREATE TRIGGER loyalty_benefit_use_append_only
  BEFORE UPDATE OR DELETE ON loyalty_benefit_use
```
