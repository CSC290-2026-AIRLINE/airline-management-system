# Feature 5 - Checkout, Payment and Refunds (Iteration-03)

Oct 28, 2026 · @Zayar

Feature 5 turns a held booking into a paid ticket (5a) and returns money correctly when a booking is cancelled, a flight is cancelled or staff decide compensation is owed (5b). It also collects payment for cargo bookings (feature 17) and for the cash part of miles bookings (feature 11). It uses Stripe in test mode only.

## Prototypes

An interactive UI prototype covers the desktop pages and the two mobile pages, except Review & Pay: [Feature 5 — Checkout, Payment & Refunds UI](https://claude.ai/artifact/QmbobFhwoEhDpn8wTyt7SC). Open it and press Play to click through. Review & Pay belongs to Features 3 and 17 and is already in their prototypes, so it is not repeated here; Feature 5 only asks them to add the voucher box to it. The payment result page switches between processing, paid, failed, paid with miles, cargo paid, capture stalled and hold-expired, and Refund Detail lets you approve, issue as voucher or reject. It is a visual guide for layout and states, not production code. It matches this review: amounts are in USD, the cargo page follows Feature 17 (15-minute hold, Air Waybill at capture), and there are states for paid with miles and capture stalled. The dashed "Demo only" strip at the top of the payment result page is a prototype control for switching examples, not part of the product. The checkout and account headers are separate: payment pages have no account links, and Receipts, My refunds and My vouchers sit under My account. The crew pay pages are marked as a stretch feature.

## Overview

Feature 5 is the money module. **5a Checkout & payment states** takes a held booking, a cargo booking or another purchasable item, lets the customer pay through Stripe, and tells feature 3 to confirm only when the money is safe. **5b Refunds & compensation** returns money for a customer cancel, or an airline flight cancel, and issues vouchers when staff decide compensation is owed. It has three actors:

**Scope widened after review.** Feature 5 is also the system's financial gateway. Beyond tickets and cargo it writes every money movement to an append-only finance journal that the finance group reads in-process (see Finance interface and money map), and it reads Stripe's rules into its design (see Stripe rules we design around). Crew pay (5c, with feature 8) is a **stretch** item: it has its own tables and its own SQL file, and the core (5a and 5b) works without it.

- **Customer**: pays at checkout with a card or wallet (a shipper does the same for a cargo booking, and a member pays the taxes and carrier charges of a miles booking this way), optionally redeems a compensation voucher, gets a receipt and invoice, requests a refund and checks its status.
- **Staff (agent / admin)**: processes refunds, part-refunds and fee waivers, issues compensation from a feature 13 case, and approves out-of-policy overrides (logged in feature 15).
- **System**: webhook handler, hold-expiry coordination with 3b, refund and compensation jobs on the simulation clock, and a fake payment provider for development.

**Vocabulary.** A **payment** is one attempt to collect money for one purchase. A **purchase** is what the money buys, named by the selling feature's `purchase_ref` (for example `booking:<id>`, `check_in:<id>:bags:<n>`, `cargo_booking:<id>`). A **payment line** is one charge inside a payment (fare, award fee, seat fee, baggage, upgrade, onboard order, cargo freight, cargo surcharge). A **refund** returns money to the original payment method, split per line. A **compensation voucher** is single-use credit. All amounts are `NUMERIC(12,2)` in the base currency (USD, from Feature 4's `pricing_setting`), and each payment and voucher keeps a `currency` snapshot. Only the Stripe provider converts to minor units, using the currency's exponent (USD 2, JPY 0), never a fixed ×100.

**Decisions agreed for this iteration.**

1. **Authorise, confirm, then capture.** Checkout only authorises the card. 5a then calls the selling feature's `confirm(purchase_ref)` (for a booking, feature 3's confirm). Capture happens only on a yes; on a refusal 5a voids the authorisation, so no refund, fee or delay. Feature 3's text changes in several places for this (see Dependencies).
2. **Hosted Stripe Checkout.** The customer is sent to a Stripe-hosted page, which also offers Apple Pay, Google Pay and Link. Card data never touches our servers. A hosted session cannot expire in under 30 minutes, so 5a expires it through Stripe's API when the hold ends (see Problems ahead). Feature 5 builds no Pay page and no hosted-checkout page: the selling feature's Review & Pay holds the Pay button, and its own confirmation page is the success URL.
3. **Vouchers are single-use and redeemed whole.** The unused balance is forfeited.
4. **Partner rebook fare difference defaults to 0.** Staff can enter an amount; the approval is logged in feature 15's `audit_log`.
5. **One checkout, several purposes.** The selling features (3b, 6, 12 and 17) give 5a the lines, the amount, the deadline and a `confirm(purchase_ref)` method; 5a never prices anything. `payment_line` carries fare, award fee, seat fee, baggage, upgrade, onboard order and cargo lines. Baggage and upgrades come from feature 6, not feature 10.
6. **A coupon line is the coupon's `price_total`.** It already includes a seat chosen while booking. A `seat_fee` line exists only for a seat bought after booking.
7. **Miles bookings pay their cash part here.** A real award ticket still owes taxes and carrier charges. Feature 4 prices them, 3b copies them into the award coupon's `price_total`, and 5a collects them as `award_fee` lines. If nothing is due, 5a records a **zero-cash payment** (provider `none`, amount 0.00, allowed only for source 3) so the booking still gets a receipt that says "Paid with N miles". Miles never pass through Feature 5: feature 11 holds and returns them.
8. **Cargo follows feature 17.** The shipper authorises, 17's `confirm` moves the booking from `held` to `booked` inside its 15-minute hold, and 5a captures at once; the Air Waybill is issued at capture. There is no `awaiting_payment` or `pending_acceptance` state. A refund happens only when 17 cancels the booking.
9. **Features call each other in-process.** The contracts are service methods, not HTTP `/internal` routes, so there is no `Sys` guard.
10. **Crew pay is a stretch item** (see Crew pay and overtime), and the finance journal is read by summing `occurred_at`, never by a "last seq seen" cursor.

**Out of scope.** Real card data or live Stripe keys, currency conversion at charge time (display conversion stays in feature 4), miles balances and goodwill miles (feature 11 holds and returns miles; 5a collects only the cash part of a miles booking), and chargebacks.

## Data model

Eleven tables carry Feature 5's core data, and four more (crew pay) are a stretch; all names are singular. `payment` links to feature 3's `booking` and `booking_coupon`, feature 17's `cargo_booking` and feature 7's `customer` through cross-module foreign keys kept in the cross-module section of the SQL. Feature 5 never copies names, passports or card numbers. Stripe holds the card; we keep only the provider ids and the card brand and last four digits for the receipt. Money is `NUMERIC(12,2)` in the base currency.

**Deliberately excluded:** card numbers or CVC (never stored), a double-entry ledger, chargebacks and disputes, multi-currency charging, saved payment methods, and miles balances (feature 11). Rows are never deleted: a payment ends in a status, and a mistaken refund is rejected by a staff decision (with a note), not removed. All business timestamps come from the simulation clock; Stripe's own timestamps are stored separately as real-clock `received_at` and never compared with simulation time.

## Checkout & payment states (5a)

A customer pays in five moves: create the payment, authorise at Stripe, ask the selling feature to confirm, capture, then issue the receipt. The money is only captured after the seller has said yes, so a refused confirm never costs the customer anything. 5a never prices: it copies the lines, the amount and the deadline from the selling feature (3b, 6, 12 or 17).

1. **Create.** Review & Pay calls `POST /checkout` with the booking reference, an `Idempotency-Key` header and an optional voucher code. 5a reads the booking from feature 3 (`getBooking(ref)`: status, `payment_type`, `hold_expires_at` and the coupons with their `price_total`), checks it is `held`, owned by the payer and has at least `min_hold_minutes` (3) of hold left, then writes the `payment` (status `created`, with its `purchase_ref`) and one `payment_line` per coupon (the coupon's `price_total`) plus one per seat bought after booking (the fee comes from feature 4). The same key from the same customer returns the existing payment instead of creating a second one, and a purchase can have only one live payment.
2. **Voucher.** If a code is given, 5a locks the voucher row, checks it is `active`, unexpired and the customer's own, and reserves it by setting `payment.voucher_id`. `voucher_amount` is the lesser of the voucher value and the total; the rest is `card_amount`. A voucher worth more than the total is still consumed whole and the difference is forfeited, and the page warns before the customer pays. If `card_amount` is 0 the payment skips Stripe and goes straight to step 4 with provider `none`. An award booking with no taxes due is a **zero-cash payment** (amount 0.00, source 3 only): 5a calls confirm, then records the payment as `captured` and issues a receipt that says "Paid with N miles"; no payment message is sent for it.
3. **Authorise.** 5a creates a Stripe Checkout Session in `payment` mode with `payment_intent_data[capture_method]=manual`, the amount converted to the currency's minor units, `metadata.payment_id` and success and cancel URLs, and returns the hosted page URL. The success URL is the selling feature's own confirmation page. The customer pays on Stripe's page with a test card. When Stripe authorises, it sends `payment_intent.amount_capturable_updated`; the webhook handler moves the payment to `authorised`. The browser returning to the success URL proves nothing; the confirmation page polls `GET /payments/:id` until a webhook has moved the status.
4. **Confirm.** On `authorised`, 5a calls the selling feature's `confirm(purchase_ref)` (for a booking, feature 3's confirm with the payment id). A yes (also for a repeat call) goes to step 5. If 3b answers `409 SEAT_UNAVAILABLE`, `HOLD_EXPIRED` or `FLIGHT_NOT_FOR_SALE`, 5a cancels the PaymentIntent (status `voided`), releases the voucher and tells the customer. Nothing was captured, so no refund is needed and there is nothing to release in 3b.
5. **Capture.** 5a captures the PaymentIntent. `payment_intent.succeeded` moves the payment to `captured`, which redeems the voucher, writes `captured_at`, creates the `receipt`, writes the `finance_posting` row and sends the payment message through feature 13. If capture fails, the purchase stays confirmed and the payment stays `authorised` with `capture_attempts` counting up; a job retries and, after `capture_retry_limit`, sets `capture_stalled_at` so the payment appears in the staff exception list (see Problems ahead). If staff cancel the booking in that window, 3b asks 5a to void the authorisation: nothing was charged, so nothing is refunded.

**Payment states.** The state moves only in one function, under a row lock on the `payment`, and only from a verified webhook, a 3b answer or a job, never from a client response.

| From | To | Trigger |
| --- | --- | --- |
| `created` | `authorised` | `payment_intent.amount_capturable_updated`, or immediately for a voucher-only payment |
| `created` | `captured` | Zero-cash payment only (source 3, provider `none`): the seller confirmed, so `authorised_at` and `captured_at` are the same moment |
| `created` | `failed` | `checkout.session.expired` or customer cancel, with no authorisation; 5a may ask 3b to release the hold early |
| `created` | `expired` | Hold ended: 5a expires the Stripe session and releases the voucher |
| `authorised` | `captured` | The seller confirmed (yes), then `payment_intent.succeeded` |
| `authorised` | `voided` | The seller refused the confirm, `payment_intent.canceled`, or 3b voided a stalled capture on a cancel |
| `captured` | `reversed` | Every line is refunded in full (a part refund leaves it `captured`). A reversed payment keeps its `purchase_ref` |
| `reversed` | `captured` | A refund fails late (`refund.failed`): the only way back |

**Webhooks.** One endpoint verifies the Stripe signature over the raw body (the app is created with `rawBody: true`), writes `payment_event_receipt` first, then applies the event. A repeat is skipped only when its receipt has `processed_at` set; a receipt with `processed_at` empty is applied again by the reconcile job. Events drive the payment as listed; any other event is stored and ignored.

| Stripe event | Effect |
| --- | --- |
| `payment_intent.amount_capturable_updated` | Attempt and payment move to `authorised`; start step 4 |
| `payment_intent.succeeded` | Payment `captured`; receipt; redeem voucher |
| `payment_intent.payment_failed` | Attempt `failed` with the failure code; the payment stays `created` so the customer can retry on the hosted page |
| `payment_intent.canceled` | Payment `voided` (or `expired`, if 5a expired it) |
| `checkout.session.expired` | Attempt closed; payment `failed` or `expired` as above |
| `refund.created`, `refund.updated`, `refund.failed` | Updates the `refund` row (see 5b) |

**Test mode only.** The team uses Stripe test keys and Stripe's published test cards for success, decline and authentication paths; no real card is ever entered. Manual capture limits which payment methods Stripe offers (cards and card-based wallets work). Every module that talks to Stripe goes through one `PaymentProvider` interface with implementations `stripe` and `fake`; `PAYMENT_PROVIDER` defaults to `fake`, so nobody needs a Stripe account or a webhook tunnel to run the app. The Stripe keys go in `.env.example` (empty) and `env.validation.ts` (see Development phases).

**Receipts.** The `receipt` is built from the finalised `payment` and its lines when the status becomes `captured`, never from the checkout request; cargo gets an invoice with the Air Waybill number, and a zero-cash award booking gets a 0.00 receipt that says "Paid with N miles" (the miles come from feature 11's redeem rows for the booking's coupons, which never change after confirm). A refund later adds a credit note; it never edits the original.

## Refunds & compensation (5b)

5b returns money in one place, whatever caused it. Every refund is a `refund` row with a unique `source_key`, split into `refund_line` rows per payment line, and executed against Stripe (or as a voucher). With authorise-then-capture, a booking that fails to confirm is voided in 5a and never reaches 5b, so 5b only handles money that was actually captured.

| Reason | Trigger | Amount | Method |
| --- | --- | --- | --- |
| `customer_cancel` | Feature 3 calls 5b's refund method when a booking is cancelled; `source_key` is `customer_cancel:<booking id>` | Coupon fare lines minus the cancellation fee from the fare rules in the coupon's `fare_rule_snapshot` (feature 4's fee method); seat fees follow the same percentage as the fare | Original method |
| `flight_cancelled` | 5b handles feature 2's `flight.cancelled` with resolution `refund`; 3b is never asked | 100% of the fare and seat fee lines of every paid coupon on that flight, no fee | Original method |
| `rebook_difference` | 3b reports a partner rebook | 0 by default; staff may enter a refund amount, approved through feature 15's `audit_log` | Original method |
| `customer_request` | The customer asks for a refund outside a cancel | Set by staff | Original or voucher |
| `staff_adjustment` | Agent or admin on the staff refund screen | Any amount up to what is still refundable; outside policy needs an admin approval | Original or voucher |
| `compensation` | Staff resolve a feature 13 case as owed (`case_compensation_id`) | Amount set by staff, capped at what is still refundable on the chosen payment | Original or voucher |
| `cargo_cancel`, `cargo_rejected`, `cargo_reweigh` | Feature 17 asks 5b when it cancels a booking, rejects a shipment or re-weighs lower | 100% and no fee before acceptance; after acceptance the fee and refundable percent from feature 17; the difference for a re-weigh | Original method |

**Customer cancel.** 3b's cancellation preview calls 5b's preview method so the customer sees the same fee and refund that 5b will pay. Cancelling then creates one `refund` against the booking's payment with a `refund_line` per coupon. A part cancel is not possible in 3b today, but the per-coupon lines keep 5b ready for it. If the booking is confirmed but its payment is only `authorised` (capture stalled), 3b asks 5a to void the authorisation instead of asking 5b for a refund.

**Flight cancelled by the airline.** 5b handles only a cancellation with resolution `refund`. It writes a `refund_event_receipt` (a foreign key to feature 2's `flight_event`) first, then finds every `payment_line` whose coupon is on that flight (payment lines point at coupons, which carry the flight, so it works whatever status 3b has set) and creates one refund per payment with `source_key = flight_cancelled:<event_id>:<payment_id>`. A replayed event finds its receipt and does nothing, and on startup 5b catches up, in `seq` order, on any such event without a receipt. For `rebook_partner` no money moves unless staff enter a negative fare difference. The airline never charges the customer more after rebooking onto a partner, so a positive difference is written off, not collected. Cargo is different: feature 17 marks its bookings `rebook_required`, and 5b refunds one only when 17 cancels it.

**Staff refunds and overrides.** Staff create a refund with a mandatory reason. If it is within policy (equal to or below what the fare rules allow) it is approved at once. If it is outside policy, after check-in, or waives a cancellation fee, it stays `pending_approval` until an admin approves it. Feature 15 has an `audit_log` but no approval step, so the approval is Feature 5's own step behind the admin guard, written to `audit_log` through feature 15's in-process audit service in the same transaction; 5b stores the entry id as `refund.audit_log_id` and keeps no audit trail of its own.

**Compensation.** When a feature 13 case resolves to "owed", feature 13 records its compensation decision (`case_compensation_id`) and calls 5b in-process; the decision id is the idempotency key. 5b pays the amount in one of two forms, answers, and feature 13 records the result and the `payout_ref`. There is no separate compensation table in Feature 5:

- **Refund to the original method.** Allowed only up to what is still refundable on the chosen payment; above that the answer is `REFUND_EXCEEDS_PAID` and staff decide on a voucher instead. A case with no customer account can only be paid as a refund.
- **Voucher.** 5b issues a `compensation_voucher` (single-use, value fixed at issue, `voucher_valid_months` (12) on the simulation clock, own-customer only). At checkout the voucher is reserved on the payment (`payment.voucher_id`) and redeemed when the payment is captured. It is released if the payment is voided, fails or expires.

**Mixed payments.** When a payment used a voucher and a card, a refund is split pro rata: the voucher share (`refund.voucher_amount`) comes back as a new voucher and the rest goes to the card, with any rounding remainder on the card.

**Execution.** A refund moves through `requested`, `pending_approval`, `approved`, `processing` and then `succeeded`, `failed` or `rejected`. 5b calls Stripe's refund endpoint with `source_key` as the idempotency key and moves to `succeeded` or `failed` only on `refund.updated` or `refund.failed`, because Stripe finishes refunds asynchronously. The `refund_line` rows are written and `payment_line.refunded_amount` raised under the payment's row lock in the same transaction. A failed refund appears in the staff exception list; staff may reissue it as a voucher with the customer's consent. When refunded amounts reach the captured total, the payment becomes `reversed` and the receipt gets a credit note for each refund; a late `refund.failed` moves it back to `captured`. Messages (`refund_issued`, `refund_failed`, `voucher_issued`) go through feature 13's `inbound_event` with source '5'.

## Miles bookings: the cash part (5a)

Feature 3 and feature 11 already book a seat with miles: 3b holds an `award` seat and feature 11 holds the miles. A real award ticket still owes cash: government taxes and the carrier's charges, plus any paid seat. Feature 4 prices the taxes and carrier charges, 3b copies them into the award coupon's `price_total`, and 5a collects them through the same checkout as `award_fee` lines. 5a never touches the miles: feature 11 holds, debits and returns them, and 5a only reads feature 11's redeem rows for the booking's coupons to print "Paid with N miles" on the receipt.

1. **Hold.** As in Feature 3, 3b holds the award seat and feature 11 holds the miles. 3b also asks feature 4 for the taxes and carrier charges per coupon and stores them as the coupon's `price_total`. There are no `cash_due` or `award_fee` columns on feature 3's tables. Nothing is charged yet.
2. **Pay.** Review & Pay shows "24,000 miles + USD 60.00" and sends the customer to Stripe's hosted page. `POST /checkout` accepts the booking because its payment type is miles and its coupons owe cash. 5a writes the payment with one `award_fee` line per coupon (its `price_total`), plus seat fees if any. A voucher may pay part of the cash due. The minimum hold applies, and one 15-minute clock covers the seat and the miles. If no taxes are due, 3b still asks 5a for a **zero-cash payment** (amount 0.00, provider `none`): 5a calls confirm, records the payment as captured and issues the receipt "Paid with N miles".
3. **Authorise.** Same as a cash booking: hosted Stripe Checkout, manual capture, and the webhook moves the payment to `authorised`.
4. **Confirm.** 5a calls 3b's confirm with the `payment_id`. For a miles booking, 3b first confirms the redemption with feature 11, which answers no if the redemption has lapsed, and then moves the seats to sold.
5. **Capture and receipt.** On a yes, 5a captures. The receipt shows the cash lines and one extra line, "Paid with N miles", summed from feature 11's redeem rows.

**If something fails.** A refused confirm (redemption lapsed, seat gone) voids the authorisation, and 3b returns the seat and tells feature 11, which writes the `redeem_reversal` so the miles come back; there is nothing to release from 5a's side. A payment that ends `failed` or `expired` makes 5a ask 3b to release the booking early; the 15-minute job covers the rest. In every case the customer is never left with miles spent, cash taken and no ticket.

**Cancel and airline cancel.** Cancelling a miles booking is two independent calls from 3b: feature 11 returns the miles in full, and 5b refunds the cash. 5b refunds the `award_fee` lines at 100% inside the cancel window (taxes are refundable) and the seat fee by feature 4's rule. Neither call waits for the other. When the airline cancels a flight, 5b refunds every cash line at 100% from `flight.cancelled`, as for any booking; feature 11 returns the miles when 3b cancels the booking (3b asks feature 11, not a `flight.cancelled` subscription).

**Not covered.** Choosing how many miles to use and paying the rest by card (partial redemption), buying miles, and goodwill miles as compensation. These belong to feature 11.

## Cargo payments (17)

The customer here is the shipper. Feature 17 owns the rate (by weight, volume and goods type), the 15-minute capacity hold, the cargo statuses and the Air Waybill; 5a only collects and returns the money. A cargo payment uses the same `payment`, Stripe session and webhooks as a ticket, with `cargo_freight` and `cargo_surcharge` lines, and feature 17 plays the role feature 3 plays for a ticket: it provides the lines, the amount, the deadline and a `confirm` method. The card is authorised, feature 17 confirms the booking (`held` to `booked`), and 5a captures at once.

1. **Hold.** The shipper requests a booking in feature 17. 17 checks the remaining hold weight and volume (feature 9 data), works out the rate and holds the space as `held` for 15 minutes.
2. **Pay.** The shipper pays from feature 17's page. `POST /checkout` carries `cargo_booking_id`. 5a reads the booking in-process (shipper, status, lines, hold end), checks it is `held` and owned by the payer, and writes the payment with `purchase_ref` `cargo_booking:<id>`, one `cargo_freight` line plus any surcharge lines, and `expires_at` at the hold end. 17 gives the amounts; 5a never prices cargo. As for tickets, 5a expires the Stripe session when the hold ends.
3. **Authorise and confirm.** Hosted Stripe Checkout with manual ca\
pture, as for tickets. On `authorised`, 5a calls 17's `confirm(purchase_ref)`. 17 checks the space is still held and moves the booking from `held` to `booked`, or answers no and 5a voids the authorisation (no refund).
4. **Capture and invoice.** On a yes, 5a captures. `payment_intent.succeeded` moves the payment to `captured`, 17 sets `payment_id` and issues the Air Waybill at capture, and 5a issues an invoice that shows the number. If capture fails, the payment stays `authorised` with `capture_stalled_at` set and appears in the exceptions list; there is no Air Waybill yet, and staff retry the capture or cancel in 17 (which voids the authorisation).
5. **Cancel.** A refund happens only when 17 cancels a `booked` booking, whatever the cause: 17 calls 5b with `cargo_cancel` (the shipper cancels) or `cargo_rejected` (staff reject a shipment). Before acceptance the refund is 100% with no fee.

| Cargo booking (feature 17) | Payment (5a) | Moved by |
| --- | --- | --- |
| held | created | The shipper opens Pay |
| held, then booked | authorised, then captured | Stripe webhook, 17's confirm says yes, then 5a captures; 17 issues the Air Waybill at capture |
| hold ended | expired | 5a cancels the PaymentIntent |
| 17's confirm says no | voided | 5a voids the authorisation; no refund |
| cancelled or rejected by 17 | reversed (refunded) | 17 asks 5b for a `cargo_cancel` or `cargo_rejected` refund |
| flight cancelled | captured (no change) | 17 marks the booking `rebook_required`; a refund follows only if 17 cancels it |

**Hold and deadlines.** Feature 17 owns the 15-minute hold and any later deadline. 5a runs no timer of its own except the session expiry at the hold end; the money is captured only once 17 has confirmed the booking.

**Re-weigh.** If the chargeable weight is lower, 17 asks 5b for a `cargo_reweigh` refund of the difference. If it is higher, 17 raises a new charge and the shipper pays it through a second checkout with `source_feature = 17` and `purchase_ref` `cargo_reweigh:<id>`. A capture is never changed after it happens.

**Refunds (5b).** Reasons that apply to cargo. `cargo_rejected`: staff reject, 100%, no fee. `cargo_cancel`: the shipper cancels, with no fee before acceptance and, after acceptance, the fee and refundable percent from feature 17. `cargo_reweigh`: the difference after a lower weight. `staff_adjustment`: for example damaged or short-shipped goods. `compensation`: as for tickets. Source keys are per cargo booking (`cargo_rejected:<cargo booking id>`). A cancelled flight does not refund cargo by itself: 17 marks the booking `rebook_required` and 5b refunds only when 17 cancels it. After the cargo is `loaded` only staff may refund, and a refund outside the rules needs an admin approval.

**Loading and unpaid shipments.** The Air Waybill is issued at capture, so a shipment whose capture is stalled has no number and 17 does not accept it (see Problems ahead, 22).

## Finance interface and money map (5c)

The lecturer's review widened Feature 5 from payment and refund into the system's financial feature. Two groups now share it. **Feature 5** moves money between the system and the outside world (cards in, cards out) and keeps those records. **The finance group (Thit, Vivian, Laura)** owns the double-entry ledger, the chart of accounts, the operating-cost entries and the financial reports. Feature 5 keeps no accounts of its own: in the same transaction as every money movement it writes a row to `finance_posting`, an append-only journal in the same database that the finance group and feature 4's monthly summary read in-process. There is no HTTP boundary, no outbox and no send job. Crew pay (stretch) would add its own postings.

**Posting contract.** In the same database transaction that changes a payment, refund or voucher, 5 writes a `finance_posting` row; a repeat is a no-op (`INSERT ... ON CONFLICT (posting_key) DO NOTHING`). A posting says what happened, when (simulation clock) and how much, by category; it carries no account codes, so the finance group can change its chart of accounts without touching Feature 5. Amounts are positive decimals in the posting's `currency` (the base currency), and the posting type gives the direction. The table is append-only: triggers reject update, delete and truncate.

```json
{
  "posting_key": "payment_captured:3f0c...e1",
  "posting_type": "payment_captured",
  "source_type": "payment",
  "source_id": "3f0c...e1",
  "currency": "USD",
  "occurred_at": "2026-11-04T09:12:00+07:00",
  "payload": {
    "lines": [
      { "category": "fare", "amount": "124.80" },
      { "category": "seat_fee", "amount": "7.20" },
      { "category": "baggage", "amount": "9.00" }
    ],
    "voucher_amount": "0.00"
  }
}
```

Posting types: `payment_captured`, `payment_provider_fee`, `refund_succeeded`, `refund_reversed`, `voucher_issued`, `voucher_redeemed`, `voucher_expired`, `compensation_paid`; the crew pay stretch file adds `crew_pay_accrued` and `crew_pay_paid`. Voided and failed payments post nothing because no money moved. A zero-cash payment posts nothing either.

**Never in the request path, and read by `occurred_at`.** Nothing is sent and nothing waits for the finance group: the posting is part of the same transaction as the movement, so it cannot be missed or half-written. Readers sum the journal by `occurred_at` (a period or a month). They must not remember a "last `seq` seen" cursor: identity values are handed out at insert but transactions commit in any order, so such a reader could skip a row that commits late. `seq` is only a stable insert order for debugging and exports.

**What the finance group owns.** The chart of accounts, the mapping from category to account, the double-entry journal, the trial balance, per-flight profit, and the cost entries for airport fees, aircraft hours, catering and maintenance (read from features 2, 9 and 12 when a flight completes). They reconcile against Feature 5 by reading `finance_posting` summed by `occurred_at`, and against Stripe's balance transactions.

## Crew pay and overtime (5c, stretch)

**Stretch.** Crew pay does not count toward the 75% bar, so build it only after 5a and 5b work. Its tables are in a separate SQL file (`crew_pay_rate`, `pay_run`, `payroll_line`, `payout`) that can be skipped without touching the core. Crew pay is money going out, so it passes through Feature 5 like any other payout, but the work (who flew how long) belongs to feature 8 and the ledger belongs to the finance group. No real money moves: payouts use the `fake` provider. It is not yet agreed with the Feature 8 owner.

1. **Report.** Feature 8 publishes no duty events and stores no duty periods. Instead a job prices a pairing once its last leg has arrived, reading the crew assignments and derived duties in-process.
2. **Price.** The job uses `crew_pay_rate` (an hourly rate and a per-diem per crew role) and the `payment_setting` keys `overtime_threshold_hours` (default 10), `overtime_multiplier` (default 1.5) and `pay_run_override_limit`. Base pay is flight hours times the rate, overtime is duty hours over the threshold (summed over the pairing's duty days) times the rate times the multiplier, per-diem is overnights times the allowance. Each part is a `payroll_line` with `crew_id`, `pairing_id`, `quantity`, `rate`, `multiplier`, status `accrued`, and `amount = round(quantity × rate × multiplier, 2)`, half up. A pairing is priced once per line type (a unique index), so a rerun creates nothing new. The job writes a `crew_pay_accrued` posting.
3. **Pay run.** A finance user creates a `pay_run` for a period. It collects the accrued lines up to the period end (`draft`). A different finance user or an admin approves it (`approved`); a run above `pay_run_override_limit`, or one containing an adjustment, also needs an admin's `audit_log` entry (`audit_log_id`). Paying creates one `payout` per crew member (the sum of that person's lines) and marks the lines `paid`. A `crew_pay_paid` posting follows.
4. **Corrections.** A paid line never changes. A correction to a paid pairing is an `adjustment` line, positive or negative, that joins the next run. A negative net amount for a person carries to the following run.
5. **Crew view.** A crew member sees their own lines and pay runs on a read-only My Pay page. This needs crew to have sign-ins (feature 8 linking `crew.staff_id` and a crew role), which is still an open question for that owner.

&#91;image: Crew pay (stretch): from pairing to payout\]

Rounding: each line is rounded half up to two decimals and the payout is the sum of the lines; the total is never rounded again. Crew pay must not also be entered as a `staff` expense in feature 4, or it would count twice.

## Stripe rules we design around

From [Stripe's refund documentation](https://docs.stripe.com/refunds):

- Refunds go only to the original payment method, and the refunds on one charge can never total more than the charge. 5b already caps each line at what was paid. Compensation above what was paid must be a voucher; a cash goodwill payment above the charge is not possible as a Stripe refund and is out of scope.
- A payment that is only authorised cannot be refunded, only cancelled. This is why a refused confirm voids the authorisation and never creates a refund.
- Stripe does not return its processing fee on a refund. The fee is read from the capture's balance transaction, stored as `payment.provider_fee`, posted once as `payment_provider_fee` and never reversed, so the finance group sees what each refunded ticket cost.
- A refund can fail up to 30 days after it was issued, and stays pending if the Stripe balance is too low. Problem 29 covers the late failure.
- A refund shortly after a charge may appear to the customer as a reversal (the charge disappears from the statement) rather than a credit, and a card credit usually takes 5 to 10 business days. The refund pages say so.
- Not checked: whether Stripe limits how long after a charge a refund can be made, and how to send money out to people. The design does not depend on either.

## Problems ahead

Most bugs in payments come from two things happening at once, or one event arriving twice. These are the cases to design and test for before week 5.

1. Confirm runs after the payment is **authorised**, not captured. 5a calls `confirmBooking(ref)`; on a yes it captures, on a refusal it voids. This replaces "after the payment is captured" in the booking steps, including the paid-seat confirm (`confirmSeat`).
2. A payment authorised after the hold expired makes confirm try to take the seats again. If they are free the booking moves from `expired` to `confirmed` and 5a captures. If not, 3b answers `409 HOLD_EXPIRED` and 5a voids. Nothing was charged, so 3b does not call 5b.
3. `HOLD_EXPIRED_REFUNDED` is renamed `HOLD_EXPIRED` everywhere. The same applies when a flight is no longer for sale: a payment already authorised for it is voided (3b answers `409 FLIGHT_NOT_FOR_SALE`), not refunded.
4. 3b publishes `booking.expired` when the job expires a held booking, so 5a can expire the open Stripe session.
5. `booking.total_amount` stays the sum of coupon fares. A coupon's `price_total` already includes a seat chosen while booking; a seat bought later is a `seat_fee` line in 5a.
6. Dependencies, row 5b: remove "a full refund when a late payment cannot be honoured". 5b is asked only for a customer cancellation.
7. Release: after 5a voids because confirm was refused, there is nothing to release. 5a asks for `releaseBooking(ref)` only when a payment ends `failed` or `expired` and the hold should end early; the 15-minute job covers the rest.
8. Cancel: a booking that is confirmed but whose payment is only `authorised` (capture stalled) is cancelled by asking 5a to void the authorisation, not 5b for a refund. Open question: can staff cancel such a booking, and who tells 5a? Suggestion: staff use feature 3's cancel, which checks the payment and calls `voidPayment(paymentId)`.
9. `booking_coupon` gets `UNIQUE (id, booking_id)` so a payment line proves its coupon belongs to the payment's booking.

**More changes, for miles bookings:**

- At hold, 3b gets the taxes and carrier charges per coupon from feature 4 and stores them as the award coupon's `price_total`. There is no `cash_due` on the booking and no `award_fee` column on the coupon. Drop `CHECK (fare_quote_id IS NOT NULL OR price_total = 0)` and its comment: an award coupon has no quote but can have a price above 0.

## Backend rules and API routes

### Backend rules (not database constraints)

- **Amounts.** `NUMERIC(12,2)` in the base currency with a `currency` snapshot; only the Stripe provider converts to minor units, by the currency's exponent. `payment_line` amounts sum to `amount_total`, and `amount_total = voucher_amount + card_amount`. A line is copied from the selling feature or fee quote and never recomputed. `amount_total` may be 0.00 only for source 3 (zero-cash award booking).
- **Create.** A payment is created only for a booking that is `held`, owned by the payer, and has at least `min_hold_minutes` (3) of hold left; otherwise `409 HOLD_TOO_SHORT`. `payment.expires_at` is the booking's `hold_expires_at` (or the selling feature's deadline).
- **One live payment.** At most one `payment` in `created`, `authorised`, `captured` or `reversed` per `(source_feature, purchase_ref)` and one open `payment_attempt` per payment, backed by partial unique indexes. A payment that ended unpaid frees the `purchase_ref`; buying again after a full refund uses a new one.
- **Idempotent create.** `POST /checkout` takes an `Idempotency-Key` header; a repeat by the same customer returns the existing payment and, if still open, its session URL.
- **State moves.** One function applies every state change, takes the `payment` row lock, and moves forward only (see Payment states). Triggers are verified webhooks, the seller's answers and jobs; a client response never moves a state.
- **Authorise, confirm, capture.** The seller's confirm is called only from `authorised`. Capture is called only after a yes. Capture amount equals `card_amount`. If capture fails `capture_retry_limit` times, set `capture_stalled_at`; a cancel in that window makes 3b ask 5a to void the authorisation.
- **Webhooks.** Verify the signature over the raw body with a tolerance of 5 minutes on the real clock; bad signature returns `400`. Insert `payment_event_receipt` first and return `200` only after the transaction commits. A repeat is skipped only if `processed_at` is set; one with `processed_at` empty is applied again. Unknown events are stored and ignored.
- **Reconciliation.** A job on the real clock re-reads from Stripe any payment in `created` or `authorised` for more than 2 minutes, and any refund in `processing` for more than 2 minutes, and applies receipts with `processed_at` empty.
- **Hold end.** When 3b publishes `booking.expired` (or the hold time passes on the simulation clock), 5a expires the open session, voids an `authorised` payment whose confirm was refused, and frees the voucher.
- **Refundable amount.** Per line: `amount - refunded_amount`. `refunded_amount` is raised under the payment's row lock in the same transaction that writes the `refund_line`; a test checks it equals the sum of the line's refund lines. A refund is accepted only if every `refund_line` fits; otherwise `422 REFUND_EXCEEDS_PAID`. Voided, failed and expired payments cannot be refunded.
- **Fees.** A cancellation fee comes from feature 4's fee method for the coupon's `fare_rule_snapshot` at the simulation time of the request. The fee is stored on the refund (`fee_withheld`) so the amount can be explained later.
- **Policy.** A staff refund above the policy amount, after check-in, or with a waived fee needs an admin approval with a mandatory reason, written to feature 15's `audit_log` in the same transaction, or it stays `pending_approval`.
- **Mixed payments.** Refund split pro rata between voucher and card; the voucher share returns as a new voucher; rounding remainder goes to the card.
- **Compensation.** Card refund up to what is refundable on the chosen payment; the rest only as a voucher. A feature 13 decision (`case_compensation_id`) can produce one compensation.
- **Vouchers.** Code from `A-Z` and `2-9` without `I` and `O`, 10 characters, random with retry. Single-use, own customer only, `voucher_valid_months` (12) on the simulation clock, redeemed whole, one voucher per checkout. Reserved on the payment at checkout, redeemed on `captured`, free again on `voided`, `failed` or `expired`.
- **Airline cancel.** 5b handles a `flight.cancelled` with resolution `refund` once per `flight_event` (stored in `refund_event_receipt`), from its own `payment_line` rows, and catches up in `seq` order on startup. It never asks 3b to confirm coupon state first, and 3b never asks 5b.
- **Ownership.** A customer reaches only their own payments, refunds and vouchers; any other id answers `404`. Staff reach all.
- **Receipts.** Created once when a payment becomes `captured`, numbered from a sequence. A refund adds a credit note; the original is never edited.
- **Test mode guard.** On startup the Stripe provider refuses to run if the secret key does not start with `sk_test_`. Card numbers, CVC and full webhook payloads are never logged.
- **Events.** Published after the transaction commits; consumers must handle a repeat.
- **Miles bookings.** Lines are one `award_fee` per coupon (its `price_total`) plus any seat fee. 5a never reads or changes a miles balance; the receipt sums feature 11's redeem rows. If nothing is due, a zero-cash payment is recorded after a yes from confirm.
- **Cargo.** A cargo payment's `expires_at` is the 17 booking's hold end. 5a calls 17's `confirm(purchase_ref)` after authorising and captures on a yes; 17 issues the Air Waybill at capture. Refunds happen only when 17 cancels (`cargo_cancel`, `cargo_rejected`) or re-weighs lower (`cargo_reweigh`); a heavier re-weigh is a second payment `cargo_reweigh:<id>`. A capture is never changed.

-- Feature 5 (Checkout, Payment and Refunds) - core schema, revision 2. All table names are singular.
-- Covers 5a (checkout and payment) and 5b (refunds and compensation). Crew pay (5c) is a stretch and lives in a separate
-- file (feature-05-stretch-crew-pay.sql) that can be skipped without touching this one.
-- Applies on top of the repo's migrations, the Feature 6, 10 and 13 migrations, feature-3.sql and feature-17.sql:
-- payments point at feature 3's booking and coupons and at feature 17's cargo booking, and compensation is feature 13's
-- case_compensation. Uses staff (feature 1), customer (feature 7), audit_log (feature 15) and flight_event (feature 2).
-- Business timestamps (started_at, expires_at, authorised_at, captured_at, voided_at, requested_at, completed_at,
-- issued_at, redeemed_at, occurred_at, processed_at, capture_stalled_at) have no default and come from the simulation
-- clock. created_at, updated_at and received_at are real time, and the backend sets updated_at on every update.
-- Money is NUMERIC in the base currency (feature 4's pricing_setting 'base_currency'); payments and vouchers keep a
-- currency snapshot. Only the Stripe provider converts to minor units, using the currency's exponent, not a fixed x 100.
-- Rows are never deleted: a payment, refund or voucher ends in a status.

-- Settings: closed list of keys. Values are validated by the backend. capture_retry_limit is a placeholder to confirm.
CREATE TABLE payment_setting (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by UUID REFERENCES staff (id),
  CONSTRAINT payment_setting_key_check CHECK (key IN ('min_hold_minutes', 'capture_retry_limit', 'voucher_valid_months'))
);
INSERT INTO payment_setting (key, value) VALUES
  ('min_hold_minutes', '3'),
  ('capture_retry_limit', '5'),
  ('voucher_valid_months', '12');

-- Vouchers: single-use credit for one customer, redeemed whole. Issued for one feature 13 compensation decision, or for
-- the voucher share of one refund. A payment names the voucher it uses (payment.voucher_id).
CREATE TABLE compensation_voucher (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  code                 TEXT NOT NULL UNIQUE CHECK (code ~ '^[A-HJ-NP-Z2-9]{10}$'),
  customer_id          UUID NOT NULL REFERENCES customer (id),
  amount               NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
  currency             TEXT NOT NULL,                          -- base currency when issued
  status               TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'redeemed', 'expired', 'cancelled')),
  case_compensation_id UUID UNIQUE,                            -- feature 13's decision (cross-module FK)
  refund_id            UUID UNIQUE,                            -- the refund whose share it returns
  issued_at            TIMESTAMPTZ NOT NULL,
  expires_at           TIMESTAMPTZ NOT NULL,                   -- issued_at + voucher_valid_months
  redeemed_at          TIMESTAMPTZ,
  cancel_reason        TEXT CHECK (btrim(cancel_reason) <> ''),
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, customer_id),
  CHECK (num_nonnulls(case_compensation_id, refund_id) = 1),
  CHECK (expires_at > issued_at),
  CHECK ((status = 'redeemed') = (redeemed_at IS NOT NULL)),
  CHECK ((status = 'cancelled') = (cancel_reason IS NOT NULL))
);
CREATE INDEX compensation_voucher_customer_idx ON compensation_voucher (customer_id, status);
CREATE INDEX compensation_voucher_expiry_idx ON compensation_voucher (expires_at) WHERE status = 'active';

-- Payments: one attempt to collect money for one purchase. The selling feature (3b, 6, 12 or 17) gives the lines, the
-- amount, the deadline (expires_at) and purchase_ref: 'booking:<id>', 'seat_assignment:<id>', 'check_in:<id>:bags:<n>',
-- 'product_order:<id>', 'cargo_booking:<id>', 'cargo_reweigh:<id>'. 5a never prices.
-- A purchase has at most one payment that is open, paid or fully refunded (reversed), so two tabs or a double click
-- cannot pay twice, and a refund that fails late can always move a reversed payment back to captured. A payment that
-- ended unpaid (failed, voided, expired) frees the purchase_ref. Buying again after a full refund uses a new purchase_ref.
-- Zero-cash payment: an award booking with no taxes due is a payment of 0.00 on provider 'none'. 5a calls the selling
-- feature's confirm, then moves it created -> captured with authorised_at = captured_at, and issues the receipt
-- "Paid with N miles". Only source_feature 3 may be 0.00. No payment_received message is sent for it.
-- Status: created -> authorised, captured (zero-cash only), failed or expired; authorised -> captured or voided;
-- captured -> reversed (every line refunded in full). A late refund failure is the only way back from reversed.
-- capture_stalled_at: the seller confirmed, but capture failed capture_retry_limit times. The payment stays authorised
-- and shows on the staff exception list; staff retry the capture, or cancel the booking in feature 3b (3b asks 5a to void).
CREATE TABLE payment (
  id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source_feature     SMALLINT NOT NULL CHECK (source_feature IN (3, 6, 12, 17)),
  purchase_ref       TEXT NOT NULL,
  payer_customer_id  UUID REFERENCES customer (id),
  booking_id         UUID,                                     -- feature 3b's booking (cross-module FK)
  cargo_booking_id   UUID,                                     -- feature 17's cargo_booking (cross-module FK)
  voucher_id         UUID,
  idempotency_key    TEXT NOT NULL,                            -- the Idempotency-Key header of POST /checkout
  status             TEXT NOT NULL DEFAULT 'created'
                       CHECK (status IN ('created', 'authorised', 'captured', 'failed', 'voided', 'expired', 'reversed')),
  provider           TEXT NOT NULL CHECK (provider IN ('stripe', 'fake', 'none')),   -- none = nothing on the card
  currency           TEXT NOT NULL,                            -- base currency when started
  amount_total       NUMERIC(12, 2) NOT NULL CHECK (amount_total >= 0),
  voucher_amount     NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (voucher_amount >= 0),
  card_amount        NUMERIC(12, 2) NOT NULL CHECK (card_amount >= 0),
  provider_fee       NUMERIC(12, 2) CHECK (provider_fee >= 0), -- Stripe's fee from the capture's balance transaction
  capture_attempts   SMALLINT NOT NULL DEFAULT 0 CHECK (capture_attempts >= 0),
  last_error         TEXT,
  started_at         TIMESTAMPTZ NOT NULL,
  expires_at         TIMESTAMPTZ NOT NULL,                     -- the booking's hold end, or the selling feature's deadline
  authorised_at      TIMESTAMPTZ,
  captured_at        TIMESTAMPTZ,
  voided_at          TIMESTAMPTZ,
  capture_stalled_at TIMESTAMPTZ,
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE NULLS NOT DISTINCT (payer_customer_id, idempotency_key),
  UNIQUE (id, booking_id),
  UNIQUE (id, cargo_booking_id),
  FOREIGN KEY (voucher_id, payer_customer_id) REFERENCES compensation_voucher (id, customer_id),
  CHECK (amount_total = voucher_amount + card_amount),
  CHECK (amount_total > 0 OR source_feature = 3),
  CHECK ((voucher_id IS NULL) = (voucher_amount = 0)),
  CHECK ((provider = 'none') = (card_amount = 0)),
  CHECK (num_nonnulls(booking_id, cargo_booking_id) <= 1),
  CHECK ((source_feature = 17) = (cargo_booking_id IS NOT NULL)),
  CHECK (source_feature NOT IN (3, 6) OR booking_id IS NOT NULL),
  CHECK (payer_customer_id IS NOT NULL OR (source_feature = 12 AND booking_id IS NULL AND voucher_id IS NULL)),
  CHECK (expires_at > started_at),
  CHECK ((status IN ('authorised', 'captured', 'voided', 'reversed')) = (authorised_at IS NOT NULL)),
  CHECK ((status IN ('captured', 'reversed')) = (captured_at IS NOT NULL)),
  CHECK ((status = 'voided') = (voided_at IS NOT NULL)),
  CHECK (capture_stalled_at IS NULL OR status = 'authorised')
);
CREATE UNIQUE INDEX payment_one_live_per_purchase_uq ON payment (source_feature, purchase_ref)
  WHERE status IN ('created', 'authorised', 'captured', 'reversed');
CREATE UNIQUE INDEX payment_voucher_uq ON payment (voucher_id, payer_customer_id)
  WHERE voucher_id IS NOT NULL AND status IN ('created', 'authorised', 'captured', 'reversed');
CREATE INDEX payment_booking_idx ON payment (booking_id) WHERE booking_id IS NOT NULL;
CREATE INDEX payment_cargo_booking_idx ON payment (cargo_booking_id) WHERE cargo_booking_id IS NOT NULL;
CREATE INDEX payment_customer_idx ON payment (payer_customer_id, started_at DESC);
CREATE INDEX payment_reconcile_idx ON payment (updated_at) WHERE status IN ('created', 'authorised');
CREATE INDEX payment_capture_stalled_idx ON payment (capture_stalled_at) WHERE capture_stalled_at IS NOT NULL;

-- One charge inside a payment, copied from the selling feature and never recomputed. A coupon line is the coupon's
-- price_total: the fare quote's total (fare, seat chosen while booking, taxes, promo) for a cash coupon, the taxes and
-- carrier charges for an award coupon (0.00 when none are due). seat_fee is a seat bought after booking. The coupon
-- belongs to the payment's booking (composite foreign keys). The lines add up to amount_total (backend).
-- refunded_amount is a counter kept under the row lock in the same transaction that writes the refund_line, so a line
-- can never be refunded beyond what it charged. A test must check it equals the sum of that line's refund_line rows.
CREATE TABLE payment_line (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id        UUID NOT NULL REFERENCES payment (id),
  booking_id        UUID,
  booking_coupon_id UUID,                                      -- feature 3b's coupon (cross-module FK)
  line_type         TEXT NOT NULL CHECK (line_type IN (
                      'fare', 'award_fee', 'seat_fee', 'baggage', 'upgrade', 'onboard_order', 'cargo_freight',
                      'cargo_surcharge')),
  source_ref        TEXT,                                      -- the selling feature's item: bag, meal order line, ...
  description       TEXT NOT NULL,
  amount            NUMERIC(12, 2) NOT NULL CHECK (amount >= 0),
  refunded_amount   NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (refunded_amount >= 0),
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, payment_id),
  UNIQUE (payment_id, line_type, booking_coupon_id),
  FOREIGN KEY (payment_id, booking_id) REFERENCES payment (id, booking_id),
  CHECK (refunded_amount <= amount),
  CHECK (line_type NOT IN ('fare', 'award_fee', 'seat_fee') OR booking_coupon_id IS NOT NULL),
  CHECK (booking_coupon_id IS NULL OR booking_id IS NOT NULL)
);
CREATE INDEX payment_line_payment_idx ON payment_line (payment_id);
CREATE INDEX payment_line_coupon_idx ON payment_line (booking_coupon_id) WHERE booking_coupon_id IS NOT NULL;

-- One Stripe Checkout Session. A decline leaves it open (the customer can try again on the same page), with the last
-- failure_code; a new attempt is made only after 5a has expired the old session. One attempt is open, and one is
-- authorised, per payment.
CREATE TABLE payment_attempt (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id          UUID NOT NULL REFERENCES payment (id),
  provider_session_id TEXT NOT NULL UNIQUE,
  provider_intent_id  TEXT UNIQUE,                             -- known once the customer starts paying
  status              TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'authorised', 'failed', 'expired', 'cancelled')),
  failure_code        TEXT,
  card_brand          TEXT,
  card_last4          TEXT CHECK (card_last4 ~ '^[0-9]{4}$'),  -- the last four only, never the number
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX payment_attempt_one_open_uq ON payment_attempt (payment_id) WHERE status = 'open';
CREATE UNIQUE INDEX payment_attempt_one_authorised_uq ON payment_attempt (payment_id) WHERE status = 'authorised';

-- One row per verified Stripe webhook, written before the event is applied. A repeat is skipped only when its row has
-- processed_at set; a row with processed_at NULL is applied again by the reconcile job, so an event is never lost.
CREATE TABLE payment_event_receipt (
  provider_event_id TEXT PRIMARY KEY,                          -- Stripe evt_...
  event_type        TEXT NOT NULL,
  payment_id        UUID REFERENCES payment (id),
  received_at       TIMESTAMPTZ NOT NULL DEFAULT now(),        -- real clock
  processed_at      TIMESTAMPTZ
);
CREATE INDEX payment_event_receipt_unprocessed_idx ON payment_event_receipt (received_at) WHERE processed_at IS NULL;

-- Refunds: one refund request. source_key makes it idempotent: 'customer_cancel:<booking id>',
-- 'flight_cancelled:<flight event id>:<payment id>', 'cargo_rejected:<cargo booking id>', 'reissue:<refund id>'.
-- voucher_amount is the share returned as a new voucher (all of it when method is voucher); the rest goes back to the
-- card through Stripe. fee_withheld is the cancellation fee kept, from feature 4's fee method.
-- A compensation refund pays one feature 13 decision. A refund outside policy waits in pending_approval until an admin
-- approves it; the approval is written to feature 15's audit_log in the same transaction (audit_log_id).
-- Status: requested or pending_approval -> approved or rejected; approved -> processing -> succeeded or failed.
CREATE TABLE refund (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id           UUID NOT NULL REFERENCES payment (id),
  source_key           TEXT NOT NULL UNIQUE,
  reason               TEXT NOT NULL CHECK (reason IN (
                         'customer_cancel', 'flight_cancelled', 'rebook_difference', 'customer_request', 'staff_adjustment',
                         'compensation', 'cargo_cancel', 'cargo_rejected', 'cargo_reweigh')),
  method               TEXT NOT NULL DEFAULT 'original' CHECK (method IN ('original', 'voucher')),
  status               TEXT NOT NULL DEFAULT 'requested'
                         CHECK (status IN ('requested', 'pending_approval', 'approved', 'processing', 'succeeded', 'failed', 'rejected')),
  amount               NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
  voucher_amount       NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (voucher_amount >= 0),
  fee_withheld         NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (fee_withheld >= 0),
  provider_refund_id   TEXT UNIQUE,                            -- Stripe re_...
  requested_by_user_id UUID REFERENCES "user" (id),            -- NULL for a system refund
  case_compensation_id UUID UNIQUE,                            -- feature 13's decision (cross-module FK)
  audit_log_id         UUID,                                   -- feature 15's audit_log (cross-module FK)
  decision_note        TEXT CHECK (btrim(decision_note) <> ''),
  failure_reason       TEXT,
  requested_at         TIMESTAMPTZ NOT NULL,
  completed_at         TIMESTAMPTZ,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, payment_id),
  CHECK (voucher_amount <= amount),
  CHECK (method = 'original' OR voucher_amount = amount),
  CHECK (provider_refund_id IS NULL OR voucher_amount < amount),
  CHECK ((reason = 'compensation') = (case_compensation_id IS NOT NULL)),
  CHECK (status <> 'rejected' OR decision_note IS NOT NULL),
  CHECK (status <> 'failed' OR failure_reason IS NOT NULL),
  CHECK ((status = 'succeeded') = (completed_at IS NOT NULL))
);
CREATE INDEX refund_payment_idx ON refund (payment_id);
CREATE INDEX refund_queue_idx ON refund (requested_at) WHERE status IN ('requested', 'pending_approval', 'failed');
CREATE INDEX refund_processing_idx ON refund (updated_at) WHERE status = 'processing';

-- How a refund splits across the lines of its own payment.
CREATE TABLE refund_line (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  refund_id       UUID NOT NULL,
  payment_id      UUID NOT NULL,
  payment_line_id UUID NOT NULL,
  amount          NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
  UNIQUE (refund_id, payment_line_id),
  FOREIGN KEY (refund_id, payment_id) REFERENCES refund (id, payment_id),
  FOREIGN KEY (payment_line_id, payment_id) REFERENCES payment_line (id, payment_id)
);
CREATE INDEX refund_line_payment_line_idx ON refund_line (payment_line_id);
ALTER TABLE compensation_voucher ADD CONSTRAINT compensation_voucher_refund_fk FOREIGN KEY (refund_id) REFERENCES refund (id);

-- Feature 2's flight events that 5b has handled (cancelled with resolution refund). A repeat finds its row and is
-- skipped. On startup the backend handles, in seq order, every such flight_event without a row here.
CREATE TABLE refund_event_receipt (
  event_id     UUID PRIMARY KEY,                               -- feature 2's flight_event (cross-module FK)
  processed_at TIMESTAMPTZ NOT NULL
);

-- Documents: a receipt (tickets and purchases) or an invoice (cargo) once per captured payment, and a credit note per
-- succeeded refund. Built from the finalised rows, never from the request, and never edited. A receipt may be 0.00
-- (a zero-cash award booking, "Paid with N miles"); an invoice or credit note is above 0.
CREATE SEQUENCE receipt_number_seq;
CREATE TABLE receipt (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id      UUID NOT NULL REFERENCES payment (id),
  refund_id       UUID,
  document_type   TEXT NOT NULL CHECK (document_type IN ('receipt', 'invoice', 'credit_note')),
  document_number TEXT NOT NULL UNIQUE,                        -- formatted by the backend from receipt_number_seq
  amount          NUMERIC(12, 2) NOT NULL CHECK (amount >= 0),
  billing_name    TEXT,                                        -- wiped on account deletion; amounts are kept
  issued_at       TIMESTAMPTZ NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (refund_id, payment_id),                              -- one credit note per refund
  FOREIGN KEY (refund_id, payment_id) REFERENCES refund (id, payment_id),
  CHECK ((document_type = 'credit_note') = (refund_id IS NOT NULL)),
  CHECK (amount > 0 OR document_type = 'receipt')
);
CREATE UNIQUE INDEX receipt_one_per_payment_uq ON receipt (payment_id) WHERE refund_id IS NULL;

-- Finance journal: append-only record of every money movement, written in the same transaction as the movement. The
-- finance module and feature 4's monthly summary read it in-process and sum it by occurred_at; nothing is sent and
-- nothing waits for them. Do not read it with a "last seq seen" cursor: transactions commit in any order, so such a
-- reader could skip a row that commits late. seq is only a stable insert order for debugging and exports.
-- posting_key makes a repeat a no-op (INSERT ... ON CONFLICT (posting_key) DO NOTHING). No account codes.
CREATE TABLE finance_posting (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  seq          BIGINT GENERATED ALWAYS AS IDENTITY UNIQUE,
  posting_key  TEXT NOT NULL UNIQUE,                           -- e.g. 'payment_captured:<payment id>'
  posting_type TEXT NOT NULL,
  source_type  TEXT NOT NULL,
  source_id    UUID NOT NULL,
  currency     TEXT NOT NULL,
  payload      JSONB NOT NULL,                                 -- {"lines": [{"category": "fare", "amount": "120.50"}], ...}
  occurred_at  TIMESTAMPTZ NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT finance_posting_posting_type_check CHECK (posting_type IN (
    'payment_captured', 'payment_provider_fee', 'refund_succeeded', 'refund_reversed', 'voucher_issued',
    'voucher_redeemed', 'voucher_expired', 'compensation_paid')),
  CONSTRAINT finance_posting_source_type_check CHECK (source_type IN ('payment', 'refund', 'compensation_voucher'))
);
CREATE INDEX finance_posting_occurred_idx ON finance_posting (occurred_at);
CREATE INDEX finance_posting_source_idx ON finance_posting (source_type, source_id);
CREATE TRIGGER finance_posting_append_only BEFORE UPDATE OR DELETE ON finance_posting
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();
CREATE TRIGGER finance_posting_no_truncate BEFORE TRUNCATE ON finance_posting
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();
